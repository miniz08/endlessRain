# 第五章系统测试答辩说明

## 1. 总体口径

第五章不要被讲成“完整生产级测试报告”，而应讲成“毕业设计原型系统的系统级验证”。它证明的是：

```text
核心业务闭环可以跑通；
关键权限和异常路径有被验证；
推荐、审计、通知、聊天等跨服务链路有测试证据；
测试发现过真实缺陷，并完成了针对性修复与复验。
```

答辩时最稳的说法是：

> 本章测试以黑盒接口测试为主，辅以前端冒烟测试、WebSocket 测试、压力测试和推荐专项数据验证。测试重点不是证明系统已经达到生产级质量，而是证明主要功能闭环、权限边界、推荐闭环和审计追踪在当前原型中具备可运行、可复现、可解释的验证结果。

## 2. 第五章最容易被问的问题

### 问题一：为什么测试内容看起来不够完整？

回答口径：

> 第五章保留的是和论文核心目标直接相关的系统级测试。由于毕业设计篇幅有限，正文没有把所有接口的逐项结果全部展开，而是选取注册登录、文章审核、互动通知、聊天、推荐、审计和压力测试这些能代表系统闭环的部分。更细的逐项结果保存在 `docs/test-execution-2026-05-12/raw` 和 `docs/recommendation-display-test-2026-05-12/raw` 中。

补一句承认不足：

> 目前单元测试、长期稳定性测试、真实用户测试和系统性渗透测试还不充分，这是后续完善方向。

### 问题二：为什么 AI 测试使用 Mock Provider？

回答口径：

> Mock Provider 不是用来证明大模型语义能力，而是用来保证系统测试可重复。系统测试关注的是文章发布后是否能触发审核、审核结果是否能更新文章状态、标签和评分是否能落库、推荐和用户评分是否能继续使用这些结构化结果。如果测试直接依赖外部大模型，会受网络、额度、限速和模型随机性的影响，导致同一用例不稳定。

再补充真实模型：

> 真实语义能力由 OpenAI-compatible Provider 验证。当前系统已经支持国内模型商轮询调用，实测阿里百炼 `qwen-turbo` 和百度千帆 `ernie-x1-turbo-32k` 可以返回符合预期的结构化分析结果；硅基流动当前模型返回 disabled，智谱触发速率限制。因此论文系统测试用 Mock 保证闭环稳定，真实 Provider 用于补充验证模型接入能力。

### 问题三：黑盒测试 84 个用例只通过 82 个，是否说明系统不可靠？

回答口径：

> 不能只看第一轮通过率，还要看缺陷闭环。第一轮黑盒测试通过 82/84，通过率 97.62%，失败项暴露了两个真实工程问题：公共注册接口曾允许客户端传入 `role=admin`，以及 WebSocket 经网关代理时消息未稳定送达。后续针对这两个问题做了修复，并在定向复验批次 `mp2ekb2ja267` 中 7 项全部通过。

可强调：

> 测试的价值不只是证明“没有问题”，也包括发现问题、定位原因、修复后复验。这个过程反而能说明测试不是形式化描述，而是真的执行过。

### 问题四：推荐流压力测试曾出现 500，为什么还能说推荐闭环成立？

回答口径：

> 第一次压力测试确实暴露推荐流并发写入问题。推荐流 160 次请求中 158 次成功、2 次失败，失败原因是 `reco_user_seen` 复合主键在并发首次写入时冲突。这个问题不影响推荐算法逻辑是否成立，但说明推荐热路径的并发写入方式需要优化。

修复口径：

> 修复后将 `reco_user_seen`、`reco_user_profile` 和 `reco_article_daily_stat` 等高频写入改为 MySQL 原子 `INSERT ... ON DUPLICATE KEY UPDATE`。定向复验中推荐流 160 次请求、16 并发全部返回 200，P95 约 5.03 秒。

保守评价：

> 因此结论应是：推荐功能和并发稳定性经过修复后可以通过验证，但性能仍是后续优化重点，不应夸大为高性能推荐系统。

### 问题五：推荐专项测试是不是“造数据”？

回答口径：

> 是构造数据，但这正是专项验证的目的。推荐系统需要比较不同画像用户在相同候选池中的排序差异，真实随机数据反而难以控制变量。专项测试构造 3 类画像用户、36 个作者、291 篇文章和 1021 条推荐事件，是为了验证用户画像、AI 标签、作者质量、风险过滤和已看惩罚是否按设计影响排序。

可强调结果：

> 该专项测试 13 项全部通过，验证了三类画像用户推荐主题不同、非公开内容不会进入展示流、已看文章会被降权。这能支撑论文中“推荐闭环可运行”的结论。

## 4. 可直接用于答辩的测试总结

可以这样说：

> 系统测试分为三层。第一层是综合黑盒测试，从 API 网关入口模拟用户访问，覆盖认证、文章、评论、关注、通知、推荐、AI 分析、聊天和审计等主流程。第二层是压力测试，选择网关健康检查、文章列表、推荐流和当前用户接口，验证不同并发下的可用性和延迟。第三层是推荐专项数据验证，通过构造不同画像用户和候选内容，验证推荐排序是否真的受到用户画像、AI 标签、作者质量、风险过滤和已看记录影响。

然后接：

> 第一轮综合黑盒测试 84 项通过 82 项，发现的注册提权和 WebSocket 网关转发问题已经修复；后续定向复验 7 项全部通过。压力测试暴露推荐流并发写入冲突，修复后 160 次请求、16 并发全部返回 200。推荐专项测试 13 项全部通过，说明推荐闭环在构造数据下符合预期。因此第五章的结论不是系统已经完全生产可用，而是主要功能闭环已经具备可演示和可验证能力。

## 5. 老师追问时的边界承认

答辩时应主动承认这些边界，反而更可信：

| 追问方向 | 建议回答 |
| --- | --- |
| 有没有单元测试？ | 当前以系统黑盒和专项验证为主，单元测试不足，后续可补充权限中间件、评分函数、推荐打分函数和参数校验器的单元测试。 |
| 有没有真实用户测试？ | 没有长期真实用户测试，当前数据主要来自脚本构造和开发环境验证，适合证明原型闭环，不代表真实运营效果。 |
| 有没有安全渗透测试？ | 没有完整渗透测试，但覆盖了未登录、越权、普通用户访问管理员接口、非法参数等基础安全用例。 |
| 压力测试规模是否太小？ | 是基础并发压测，不是生产容量评估。它的价值在于暴露推荐热路径并发写入问题，并完成修复复验。 |
| 为什么不把所有失败都写进论文？ | 论文正文保留关键结果和修复结论，原始报告中保留了失败记录。答辩时可以说明失败项是测试发现并已修复的问题。 |
| 推荐专项数据是否人为控制？ | 是控制变量测试，用于验证算法规则是否生效；真实运营效果需要长期用户数据继续评估。 |
| AI 测试是否真的验证大模型？ | 系统测试用 Mock 验证闭环稳定；真实模型接入已通过国内 OpenAI-compatible Provider 补充验证，但受额度和限速影响，不适合作为稳定回归测试依赖。 |

## 6. 第五章正文建议保留的重点

如果后续还要微调论文正文，建议坚持下面几个表达：

1. 不写“系统测试全部通过”，改成“主要功能通过，发现的问题已完成定向修复和复验”。
2. 不写“推荐性能良好”，改成“推荐功能正确，性能仍有优化空间”。
3. 不写“AI 审核能力完全可靠”，改成“AI 审核闭环可运行，Mock 保证测试可重复，真实模型可通过兼容 Provider 接入”。
4. 不写“测试覆盖所有情况”，改成“覆盖核心业务流程、权限边界、异常路径和推荐专项验证”。
5. 不回避失败项，说明失败项如何暴露问题、如何修复、如何复验。

## 7. 最短答辩版

如果老师只给很短时间，可以压缩为：

> 第五章测试不是生产级全量测试，而是围绕毕业设计核心闭环做系统验证。综合黑盒测试从网关入口执行 84 个用例，通过 82 个；失败项分别暴露了注册角色提权和 WebSocket 网关转发问题，后续定向复验 7 项全部通过。压力测试执行 600 次请求，发现推荐流并发写入冲突，修复后推荐流 160 次请求、16 并发全部成功。推荐专项构造 3 类画像用户、36 个作者、291 篇文章和 1021 条推荐事件，13 项验证全部通过，证明画像、标签、风险过滤和已看惩罚会影响推荐排序。因此测试结论是：系统主业务闭环可运行，关键问题有修复闭环，但性能优化、单元测试、长期真实用户测试仍是后续工作。
