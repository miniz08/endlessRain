# 三个高概率深挖点答辩稿

本文根据 `毕业论文初稿.docx` 中的摘要、1.2、4.5、4.7、4.8、5.3 和第 6 章整理。老师如果顺着论文追问，最可能集中在：

1. AI 的调用过程与运行机制。
2. 推荐闭环：推荐事件、用户画像、推荐分、展示控制。
3. 审计闭环：到底记录什么、怎么查、为什么能称为审计。

## 0. 最先要统一的答辩口径

### 这三块在论文里的共同主线

一句话概括：

```text
用户发布内容 -> AI 分析与状态控制 -> 公开内容进入推荐 -> 用户行为形成事件 -> 画像和统计更新 -> 管理员通过审计和运维页面追踪异常
```

也就是说，本系统不是只做一个发文平台，而是围绕“内容治理”做了三个闭环：

| 闭环 | 解决的问题 | 核心数据 |
| --- | --- | --- |
| AI 内容治理闭环 | 文章能不能公开、是否降权、是否复核 | `article`、`article_ai_analysis`、AI 标签表 |
| 推荐反馈闭环 | 公开内容如何排序，用户行为如何反哺推荐 | `reco_event`、`reco_user_profile`、`reco_article_daily_stat` |
| 审计追踪闭环 | 关键操作和异常如何被追踪、查询和定位 | `audit_log`、`requestId`、网关指标 |

### 两个危险表述要修正

#### 1. “推荐结果写入审计日志”

更准确的说法：

推荐请求和返回文章 ID 写入的是 `reco_request_log`，用于推荐调试和复现；审计日志 `audit_log` 主要记录登录、发文、删除、AI 分析、评论、关注、聊天、异常请求和管理员查询等关键操作。两者都能追踪系统行为，但职责不同。

#### 2. “推荐流压力来自外部大模型”

更准确的说法：

推荐流本身不实时调用大模型，它使用的是已经持久化的 AI 评分和 AI 标签。推荐流延迟较高，主要来自候选文章读取、AI 标签和评分读取、用户画像读取或刷新、近 14 天统计聚合、已看记录读取，以及曝光事件同步写入。外部大模型主要影响文章发布审核阶段，不是每次推荐请求都调用。

答辩时可以说：

“推荐模块依赖 AI 分析结果，但不是实时依赖 AI 服务。AI 服务的输出先落库，推荐流读取落库后的评分和标签。”

## 1. AI 调用过程与运行机制

### 1.1 老师为什么会问

论文多处写到“调用大模型生成友善度、理性度、合法性和专业性评分，并输出风险等级、审核建议和标签结果”。老师很可能追问：

- 什么时候调用 AI？
- 谁调用谁？
- AI 返回什么？
- 怎么保证结构化？
- 失败怎么办？
- Mock Provider 和真实 Provider 什么关系？
- AI 结果如何影响文章、用户评分和推荐？

### 1.2 一句话回答

用户发文后，博客服务先把文章保存为待审核状态，再通过内部 HTTP 调用 AI 服务；AI 服务通过 provider 调用 Mock 或真实大模型，把文本分析成四项评分、风险等级、处理决策、原因、建议和标签，最后写回文章状态、AI 分析表和 AI 标签表，供内容展示、推荐排序和用户评分使用。

### 1.3 完整流程

```text
1. 用户在前端提交文章
2. 前端请求 API 网关 `/api/articles`
3. 网关转发到 `blog_service`
4. `blog_service` 校验身份、清洗内容
5. 文章先写入 `article`，状态为 `PENDING_REVIEW`
6. `blog_service` 使用内部 token 调用 `ai_service`
7. `ai_service` 读取文章内容
8. `ai_service` 通过 provider 选择 Mock 或真实大模型
9. provider 返回结构化分析结果
10. AI 服务规范化评分、标签和决策
11. 写入 `article_ai_analysis`
12. 写入 `article_ai_tag` 和 `article_ai_tag_on_article`
13. 更新 `article.status`、`reviewDecision`、`riskLevel`、原因、建议、审核时间
14. 刷新作者 `professionalism`、`friendliness`
15. 通知模块给作者发送审核结果
```

### 1.4 AI 服务返回什么

核心返回字段：

| 字段 | 含义 |
| --- | --- |
| `friendlinessScore` | 友善度 |
| `rationalityScore` | 理性度 |
| `legalityScore` | 合法性 |
| `professionalismScore` | 专业性 |
| `riskLevel` | 风险等级 |
| `decision` | 处理决策 |
| `tags` | AI 标签、置信度、权重 |
| `reason` | 原因 |
| `suggestion` | 建议 |
| `provider`、`model` | 使用的 provider 和模型 |

答辩时重点说：

AI 不是只返回一段自然语言，而是返回可落库、可参与后续计算的结构化结果。

### 1.5 四项评分为什么这样设计

| 评分 | 答辩解释 |
| --- | --- |
| 友善度 | 评价表达是否友好，维护社区氛围 |
| 理性度 | 评价是否有攻击性、极端化或情绪化表达 |
| 合法性 | 判断内容是否存在违规或安全风险，是状态控制的主要依据 |
| 专业性 | 衡量内容质量，参与用户评分和推荐排序 |

可以补一句：

合法性决定安全底线，其他三个指标更多用于内容质量和推荐质量判断。

### 1.6 风险等级和文章状态如何映射

当前代码主要依据合法性分做决策：

| 合法性分 | 风险等级 | AI 决策 | 文章状态 |
| --- | --- | --- | --- |
| >= 80 | `LOW` | `ALLOW` | `PUBLISHED` |
| >= 60 | `MEDIUM` | `LOW_PRIORITY` | `LOW_PRIORITY` |
| >= 40 | `HIGH` | `REVIEW` | `REVIEW_REQUIRED` |
| < 40 | `BLOCK` | `REJECT` | `REJECTED` |

答辩口径：

系统把“内容质量评价”和“展示状态控制”分开。AI 给出评分和决策，系统再按规则映射为文章状态，避免完全依赖模型自由输出。

### 1.7 如何保证 AI 返回结构化

真实 Provider 的做法：

- prompt 要求只输出 JSON。
- 使用 OpenAI-compatible 接口。
- 请求中设置 `response_format: { type: "json_object" }`。
- 服务端再次解析 JSON。
- 对分数做 `normalizeScores`，限制到 0 到 100。
- 对标签做 `normalizeTags`，只接收预设标签体系中的结果。

如果老师问“模型乱返回怎么办”：

如果 JSON 解析失败、字段缺失、模型异常或超时，AI 服务会进入保守 fallback，返回偏低分数、`HIGH` 风险和 `REVIEW` 决策，让文章进入复核，而不是直接公开。

### 1.8 Mock Provider 与真实 Provider

| 类型 | 作用 |
| --- | --- |
| Mock Provider | 本地规则，结果稳定，用于测试和答辩演示 |
| OpenAI-compatible Provider | 调用真实大模型，用于真实语义分析 |
| fallback | provider 失败时的保守降级 |

答辩时不要说 Mock 等于真实 AI。应该说：

Mock 验证的是系统流程稳定性，真实 Provider 验证语义分析能力。两者遵守同一套结构化输出协议，所以后续可以替换。

### 1.9 AI 结果被哪些模块使用

| 模块 | 使用方式 |
| --- | --- |
| 内容发布 | 决定文章公开、降权、复核或拒绝 |
| 通知反馈 | 把审核结果、风险等级、原因和建议通知作者 |
| 用户评分 | 内容质量分、合规分、作者基础专业度和友好度 |
| 推荐系统 | AI 标签用于标签匹配，合法性分用于风险惩罚，四项评分用于内容质量 |
| 管理审计 | AI 分析操作会写入审计日志，管理员可查看分析结果 |

### 1.10 AI 深挖问答

#### Q1：AI 服务为什么单独拆出来？

AI 分析和普通内容接口的计算特点不同，可能慢、可能失败，也可能后续替换模型。单独拆成 `ai_service` 可以隔离复杂度，也方便替换 Mock、真实模型或未来私有模型。

#### Q2：AI 分析是同步还是异步？

当前发文后会同步触发 AI 分析，但文章先以 `PENDING_REVIEW` 入库，确保未审核内容不会提前公开。后续如果并发增大，可以改为消息队列异步处理。

#### Q3：如果 AI 判断错了怎么办？

系统没有把 AI 当成绝对裁判，而是保留 `REVIEW_REQUIRED`、原因、建议和管理员查看能力。误判可以通过人工复核纠正，这是后续完善方向。

#### Q4：AI 是否参与模型训练？

没有。系统没有训练自己的模型，而是通过 provider 调用外部大模型或 Mock Provider。论文重点是 AI 分析能力的工程接入和治理闭环。

#### Q5：为什么合法性分是核心？

因为合法性对应平台安全底线。友善度、理性度、专业性影响内容质量和推荐排序，但是否公开首先要看内容是否安全合规。

## 2. 推荐流程闭环

### 2.1 老师为什么会问

论文 4.7 写得很细，包含推荐事件、用户画像、推荐分公式、90 天 500 条事件、14 天统计、已看惩罚、风险惩罚。老师很可能会要求你把整个链条讲清楚，而不是只背公式。

### 2.2 一句话回答

推荐系统先过滤掉不可展示文章，再读取用户画像、文章 AI 标签、作者质量、内容质量、时间新鲜度、风险等级和已看记录计算推荐分；用户后续的曝光、点击、停留、点赞、评论、收藏、关注、隐藏和举报会写入推荐事件，并反过来更新用户画像、文章日统计和已看记录，影响下一次推荐。

### 2.3 推荐完整闭环

```text
文章发布
  -> AI 分析生成评分和标签
  -> 文章状态变为 PUBLISHED / LOW_PRIORITY / REVIEW_REQUIRED / REJECTED
  -> 推荐流只选择公开状态文章
  -> 读取用户画像、AI 标签、作者质量、内容质量、统计数据、已看记录
  -> 计算推荐分并排序
  -> 返回推荐列表
  -> 记录推荐请求 `reco_request_log`
  -> 记录曝光事件 `reco_event`
  -> 更新 `reco_user_seen`
  -> 用户点击、停留、点赞、评论、收藏、关注、隐藏、举报
  -> 再写入 `reco_event`
  -> 更新 `reco_article_daily_stat`
  -> 刷新 `reco_user_profile`
  -> 下一次推荐结果变化
```

### 2.4 推荐分之前为什么要先做展示控制

答辩重点：

推荐算法只能决定排序，不能决定权限。系统先判断文章“能不能展示”，再判断“排在第几”。如果不先过滤，审核中或拒绝的内容可能因为标签匹配被推荐出去。

可进入候选的文章：

```text
PUBLISHED
LOW_PRIORITY
```

不能进入普通推荐的文章：

```text
PENDING_REVIEW
REVIEW_REQUIRED
REJECTED
legalityScore < 40
```

### 2.5 推荐请求流程

```text
1. 用户访问推荐页
2. 网关转发到 `blog_service`
3. 服务读取 userId、limit、cursor、requestId
4. 登录用户读取画像
5. 画像不存在或超过 6 小时则刷新
6. 加载候选文章，数量为 max(80, limit * 8)
7. 并行读取：
   - reaction 汇总
   - 评论数量
   - 最近 14 天文章日统计
   - 用户已看记录
8. 对候选文章逐篇计算推荐分
9. 按分数降序排序
10. 返回前 limit 条
11. 写入推荐请求记录和曝光事件
```

### 2.6 推荐总分公式

```text
推荐总分 =
  标签匹配分 * 4
  + 作者亲和度 * 2
  + 作者质量分 * 1.2
  + 内容质量分
  + 时间新鲜度
  - 风险惩罚
  - 已看惩罚
```

一句话解释：

系统把用户兴趣、作者偏好、作者质量、内容质量、新鲜度和安全风险放在同一个可解释公式里，而不是单纯按时间或热度排序。

### 2.7 每个分项怎么讲

| 分项 | 来源 | 作用 |
| --- | --- | --- |
| 标签匹配分 | 用户 `tagVector` 与文章 AI 标签 | 判断主题是否符合兴趣 |
| 作者亲和度 | 用户过去对该作者的行为 | 判断是否偏好某作者 |
| 作者质量分 | 作者专业度和友好度 | 优先展示高质量作者 |
| 内容质量分 | AI 四项评分 + 近期互动统计 | 评价文章本身质量 |
| 时间新鲜度 | 发布时间指数衰减 | 给新内容曝光机会 |
| 风险惩罚 | 合法性分、低优先级状态 | 防止风险内容被放大 |
| 已看惩罚 | `reco_user_seen` | 减少重复曝光 |

### 2.8 推荐事件如何生成

推荐事件有两类来源：

#### 1. 推荐系统自动生成

推荐流返回文章后，会把返回给用户的文章记录为 `IMPRESSION`，并写入：

- `reco_event`
- `reco_user_seen`
- `reco_article_daily_stat`

#### 2. 用户主动行为生成

用户后续行为也会写入 `reco_event`：

```text
CLICK
DWELL
READ_COMPLETE
LIKE
COMMENT
FAVORITE
FOLLOW_AUTHOR
HIDE
REPORT
```

其中 `CLICK`、`DWELL`、`READ_COMPLETE`、`LIKE`、`COMMENT`、`FAVORITE`、`FOLLOW_AUTHOR`、`HIDE`、`REPORT` 会触发用户画像刷新。

### 2.9 推荐事件的权重

画像计算时的权重：

| 事件 | 权重 |
| --- | ---: |
| `IMPRESSION` | 0.03 |
| `CLICK` | 1 |
| `DWELL` | 最高 3，按停留时长计算 |
| `READ_COMPLETE` | 2 |
| `LIKE` | 3 |
| `COMMENT` | 4 |
| `FAVORITE` | 5 |
| `FOLLOW_AUTHOR` | 2.5 |
| `HIDE` | -3 |
| `REPORT` | -6 |

答辩解释：

曝光只是弱信号，收藏和评论代表更强兴趣，隐藏和举报是负反馈。这样推荐不是只学习用户喜欢什么，也学习用户不想看什么。

### 2.10 用户画像如何生成

画像来源：

```text
最近 90 天
最多 500 条推荐事件
```

计算过程：

```text
1. 读取用户最近推荐事件
2. 按事件类型给权重
3. 对旧事件做时间衰减
4. 读取事件对应文章的 AI 标签和作者
5. 累加标签兴趣 `tagVector`
6. 累加作者亲和 `authorAffinity`
7. 向量归一化
8. 写入 `reco_user_profile`
```

时间衰减：

```text
ageFactor = exp(-ageDays / 30)
finalWeight = eventWeight * ageFactor
```

答辩解释：

近期行为影响更大，历史行为逐渐减弱，避免早期兴趣长期固化。

### 2.11 `tagVector` 和 `authorAffinity` 怎么解释

| 字段 | 解释 |
| --- | --- |
| `tagVector` | 用户对不同 AI 标签的兴趣强弱 |
| `authorAffinity` | 用户对不同作者的亲近程度 |

例如：

用户经常点击和收藏“数据分析”“AI模型”标签的文章，那么这些标签在 `tagVector` 中权重上升；如果用户经常阅读某个作者，`authorAffinity` 中该作者权重上升。

### 2.12 内容质量分怎么计算

内容质量分由三部分构成：

```text
AI 内容质量
文章日统计质量
互动率
```

可答辩化解释：

AI 分数反映内容本身质量；文章日统计反映近期用户反馈；互动率避免只看绝对数量。这样一篇文章即使 AI 分高，如果被大量隐藏或举报，也会被降权。

### 2.13 风险惩罚如何避免高风险内容被放大

风险惩罚主要依据合法性分：

| 合法性分 | 处理 |
| --- | --- |
| >= 80 | 无惩罚 |
| 60-79 | 轻度惩罚 |
| 40-59 | 明显惩罚 |
| < 40 | 过滤或极大惩罚 |

答辩重点：

用户兴趣不能绕过安全规则。即使用户对某类内容感兴趣，高风险内容也不能被算法放大。

### 2.14 推荐闭环中的数据表

| 表 | 作用 |
| --- | --- |
| `article` | 文章内容、状态、发布时间 |
| `article_ai_analysis` | AI 四项评分 |
| `article_ai_tag_on_article` | 文章 AI 标签、置信度、权重 |
| `reco_event` | 原始推荐行为事件 |
| `reco_user_profile` | 用户标签向量和作者亲和度 |
| `reco_user_seen` | 用户已看次数 |
| `reco_article_daily_stat` | 文章每日曝光、点击、点赞、举报等统计 |
| `reco_request_log` | 推荐请求、候选数量、返回结果 ID |

### 2.15 推荐深挖问答

#### Q1：推荐系统是不是简单排序？

不是。它不是只按时间或热度排序，而是先做展示过滤，再综合用户画像、AI 标签、作者质量、内容质量、新鲜度、风险惩罚和已看惩罚。

#### Q2：新用户没有画像怎么办？

没有画像时，标签匹配和作者亲和度为空，但系统仍能根据内容质量、作者质量、互动统计和新鲜度排序。用户产生行为后，画像逐步形成。

#### Q3：新文章没有互动数据怎么办？

新文章仍有 AI 评分、AI 标签、作者质量和时间新鲜度。互动数据为空时不会完全没有分，只是后续会随着曝光、点击、评论等事件逐渐修正排序。

#### Q4：为什么用规则加权，不用深度学习？

因为毕业设计数据规模有限，深度学习需要大量真实数据和训练过程。当前方案可解释、成本低、能展示完整闭环，更符合课题目标。

#### Q5：推荐会不会造成信息茧房？

有潜在风险。系统通过时间新鲜度、已看惩罚、负反馈和风险控制缓解，但多样性探索和随机召回还可以继续完善。

#### Q6：推荐结果如何证明画像起作用？

推荐专项测试构造了数据型、生活型、安全型 3 类画像用户，36 个作者、291 篇文章和 1021 条推荐事件。结果显示三类用户看到的主题明显不同，说明画像确实影响排序。

#### Q7：P95 5.03s 说明系统不可用吗？

不说明不可用，但说明推荐性能需要优化。功能上 160 次、16 并发全部返回 200，稳定性通过；性能瓶颈主要来自候选加载、画像刷新、统计读取和同步事件写入，后续可用缓存、异步写入、分页候选优化来改进。

## 3. 审计流程闭环

### 3.1 老师为什么会问

论文题目强调“高安全性”，4.8 又写了“安全日志记录与审计模块”。老师可能追问：

- 你到底实现了什么才叫审计？
- 只是打印日志吗？
- 审计日志记录哪些字段？
- requestId 怎么追踪？
- 管理员能看什么？
- 审计日志失败怎么办？
- 审计模块没独立成服务是否矛盾？

### 3.2 一句话回答

本系统的审计不是简单控制台日志，而是以 API 网关生成的 `requestId` 为链路标识，在各业务服务关键操作中写入 `audit_log`，管理员可以通过运维页面查看服务健康、路由指标、审计日志和失败请求摘要，并根据 requestId、用户、接口、状态码和详情定位异常。

### 3.3 审计闭环

```text
用户或管理员发起请求
  -> API 网关生成/透传 requestId
  -> 网关转发到对应服务
  -> 业务服务执行关键操作
  -> 成功或失败写入 audit_log
  -> 网关同步记录路由指标
  -> 管理员访问运维页面
  -> 查看健康检查、路由指标、审计日志、失败摘要
  -> 按 requestId / 用户 / 动作 / 状态码定位问题
```

### 3.4 为什么能称为审计

因为它具备审计的几个基本要素：

| 要素 | 系统实现 |
| --- | --- |
| 谁做的 | `userId`、`username`、`role` |
| 从哪里来 | `ipAddress` |
| 做了什么 | `method`、`route`、`action` |
| 结果如何 | `result`、`statusCode` |
| 发生时间 | `createdAt` |
| 如何串联 | `requestId` |
| 额外说明 | `detail` |
| 谁能查看 | 只有管理员可查 |

答辩重点：

审计不是只记录一条日志，而是记录“可追责、可查询、可定位”的结构化操作记录。

### 3.5 `audit_log` 记录字段

核心字段：

```text
requestId
userId
username
role
ipAddress
method
route
action
result
statusCode
detail
createdAt
```

示例动作：

```text
AUTH_REGISTER

AUTH_REFRESH
AUTH_LOGOUT

AI_ANALYSIS_ATTACHED

FOLLOW_REMOVE
CHAT_THREAD_CREATE
CHAT_MESSAGE_CREATE

```

### 3.6 requestId 怎么用

`requestId` 由网关生成或透传：

```text
客户端请求
  -> 网关生成 x-request-id
  -> 下游服务继续使用该 ID
  -> 审计日志保存该 ID
  -> 响应也带回该 ID
```

答辩解释：

当某个接口失败时，管理员可以拿响应中的 requestId 去审计日志里查同一请求的操作记录，从而定位是哪条路径、哪个用户、哪个服务、什么状态码导致问题。

### 3.7 审计覆盖哪些功能

| 模块 | 审计内容 |
| --- | --- |
| 认证 | 注册、登录、刷新、退出 |
| 内容 | 文章创建、删除、AI 审核结果 |
| AI | 文本分析、文章分析、分析持久化 |
| 评论 | 创建、删除 |
| reaction | 文章和评论反馈切换 |
| 关注 | 关注、取消关注 |
| 聊天 | 线程创建、消息发送、WebSocket 连接 |
| 网关 | 健康、路由、指标、审计查询、管理员摘要 |
| 异常 | 失败请求、状态码、错误详情 |

### 3.8 网关监控和审计日志的区别

| 项目 | 网关指标 | 审计日志 |
| --- | --- | --- |
| 关注点 | 路由整体运行情况 | 具体用户和操作 |
| 粒度 | 按路由聚合 | 按请求/动作记录 |
| 数据 | 请求次数、错误次数、方法、最后状态、延迟 | 用户、动作、结果、状态码、详情 |
| 用途 | 判断服务健康和热点接口 | 追踪具体异常和责任链 |

答辩时可以说：

网关指标解决“系统哪块不正常”，审计日志解决“谁在什么时候做了什么，结果是什么”。

### 3.9 管理员能看到什么

运维页和网关管理接口提供：

- 聚合健康检查。
- 路由列表。
- 路由指标。
- 审计日志列表。
- 管理员摘要。
- 最近失败请求。
- 热点动作和热点路由。

只有 `admin` 角色可以访问审计日志和管理员摘要，普通用户会被拒绝。

### 3.10 审计写入失败怎么办

当前策略：

审计日志写入失败只记录错误，不阻断主流程。

答辩解释：

登录、发文、评论等主流程不能因为日志系统临时异常而失败。更完善的生产方案是接入独立日志队列或外部审计系统，保证日志最终可落地。

### 3.11 审计模块为什么没独立成服务

可以这样答：

当前系统是毕业设计原型，审计功能作为横切能力分布在各业务服务中，便于快速落地和验证闭环。严格生产环境中，审计模块更适合独立成服务或接入专门日志系统，减少业务耦合并提高防篡改能力。

### 3.12 审计的不足要主动承认

当前不足：

- 审计日志存储在业务数据库中，防篡改能力有限。
- 审计模块没有独立成服务。
- 缺少日志签名、只追加存储、外部归档。
- 异常流量识别还不深入。
- WebSocket 每条消息的细粒度审计还可以加强。

稳妥口径：

“本系统实现的是毕业设计原型层面的结构化审计和运维追踪，不是生产级合规审计系统。”

### 3.13 审计深挖问答

#### Q1：你的审计和普通日志有什么区别？

普通日志多用于开发排错，可能是非结构化文本；本系统审计日志是结构化表记录，包含用户、角色、动作、结果、状态码、详情和 requestId，管理员可以查询和追踪。

#### Q2：为什么 requestId 很重要？

因为微服务一次请求可能经过网关和多个服务。requestId 是链路标识，可以把同一次请求在不同位置的记录串起来。

#### Q3：如果攻击者删除审计日志怎么办？

当前原型无法完全防止数据库高权限攻击者篡改日志。生产环境需要数据库权限隔离、备份、外部日志系统、只追加存储和日志签名。

#### Q4：审计是否会影响性能？

有一定写入成本，但当前记录的是关键操作，不是所有细粒度行为。写入失败不阻断主流程。后续可以异步写日志降低影响。

#### Q5：审计模块没独立出来，为什么还算安全设计？

因为它已经实现了请求追踪、关键操作记录、管理员查询和失败摘要。独立成服务是更高等级的工程演进，不影响当前原型已经具备基础审计能力。

#### Q6：管理员如何定位一个失败请求？

先在运维页面看管理员摘要中的最近失败请求，拿到 requestId、route、statusCode 和 detail；再按 requestId 查询审计日志，判断是哪个用户、哪个动作、哪个接口失败。

## 4. 三块串起来的最终口述版

如果老师让你整体讲，可以用这一段：

本系统围绕内容治理做了一个从发布到追踪的闭环。用户发布文章后，博客服务先把文章保存为待审核状态，再通过内部接口调用 AI 服务。AI 服务通过 provider 调用 Mock 或真实大模型，生成友善度、理性度、合法性、专业性评分，以及风险等级、处理决策、原因建议和标签。系统再根据 AI 决策把文章设置为公开、低优先级、复核或拒绝。只有公开和低优先级文章可以进入推荐候选。推荐时系统读取用户画像、文章 AI 标签、作者质量、内容质量、新鲜度、风险惩罚和已看记录计算推荐分，返回结果后记录推荐请求和曝光事件。用户后续点击、停留、点赞、评论、收藏、关注、隐藏和举报会继续写入推荐事件，并更新用户画像和文章统计。与此同时，网关为请求生成 requestId，各服务把登录、发文、AI 分析、删除、评论、关注、聊天等关键操作写入审计日志，管理员可以在运维页面查看健康状态、路由指标、审计日志和失败请求，用 requestId 追踪异常链路。这样系统形成了 AI 内容治理、推荐反馈和审计追踪三个闭环。
