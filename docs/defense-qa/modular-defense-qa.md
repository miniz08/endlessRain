# 答辩疑点分模块简答稿

说明：本稿把原始问题按系统模块合并整理，回答以答辩口径为主，优先保证简洁、准确、能落到本系统实现。

## 1. 选题与系统定位

### Q1：为什么选择“基于微服务的社交平台”？

因为社交平台天然包含用户、内容、互动、推荐、通知、聊天和运维等多个相对独立的业务边界，适合用微服务思想拆分。论文重点不是只做一个博客，而是做一个包含内容治理、推荐展示和安全审计闭环的社交平台原型。

### Q2：和普通博客系统、普通社交平台的区别是什么？

普通博客偏内容发布，本系统在发布之外加入 AI 内容分析、用户综合评分、个性化推荐、通知反馈和审计日志。它更强调“内容发布后如何被审核、展示、追踪和治理”。

### Q4：“高安全性”体现在哪里？

主要体现在身份认证、角色权限、发布前审核、内容可见性控制、CSRF 防护、输入校验、请求限流、审计日志和 requestId 追踪。答辩时建议说“相对普通原型系统安全性更高”，不要说成生产级绝对安全。

### Q5：创新点是什么？

核心创新是把 AI 内容评分、用户行为评分、推荐展示控制和审计日志串成闭环。文章不是简单发布，而是先审核，再根据风险影响公开状态、推荐权重和作者质量信号。


## 2. 架构与技术选型

### Q1：为什么采用微服务而不是单体？

因为用户认证、内容管理、AI 分析、聊天和网关的职责差异明显，拆分后便于独立开发、测试和扩展。对毕业设计而言，它也更能体现工程结构和服务协作。

### Q2：系统拆成哪些服务？

前端是 `mofukaze`，后端包括 `api_gateway`、`user_service`、`blog_service`、`ai_service`、`chat_service`。其中博客服务承载文章、评论、关注、通知、推荐和画像等核心社交业务。

### Q3：API 网关的作用是什么？

网关统一暴露 `/api` 入口，负责路由转发、requestId 生成、限流、CORS、健康检查、路由指标和 WebSocket 代理。前端不需要直接感知各个后端服务端口。

### Q4：服务之间如何通信？

前端通过 API 网关访问后端；网关按路由转发到用户、博客、AI 和聊天服务；博客服务在发文后通过 HTTP 和内部 token 调用 AI 服务；聊天的实时通信用 WebSocket，经网关转发到 `chat_service`。


### Q8：Docker Compose 的作用是什么？

Docker Compose 用于统一启动前端、网关和各后端服务，简化演示和部署环境。它适合单机开发和毕业设计演示；如果是大规模生产环境，再考虑 Kubernetes。

### Q9：如果某个服务宕机会怎样？

网关宕机会影响所有外部访问；AI 服务宕机时文章会进入保守复核而不是直接公开；聊天服务宕机会影响私信；用户或博客服务宕机会影响对应业务。服务拆分让故障影响范围更清楚。


### Q15：Mock Provider 和真实大模型 Provider 的区别？

Mock Provider 是本地确定性规则，结果稳定，适合测试和演示。真实 Provider 通过 OpenAI-compatible 接口调用外部模型，效果更接近真实语义分析，但会受网络、额度、费用和返回稳定性影响。

## 3. 数据库设计

### Q1：数据库大概有多少张表？

Prisma 主 schema 中有 20 个核心模型，另有 `notification` 通过迁移 SQL 建表，整体约 21 张核心业务表。它们覆盖用户、文章、评论、关注、通知、AI 分析、推荐、聊天、认证和审计。

### Q2：数据表如何分类？

可以分为用户认证类、内容类、互动类、通知类、AI 分析类、推荐画像类、聊天类和审计类。这样分类能直接对应系统模块。

### Q3：`user` 表为什么有 `professionalism` 和 `friendliness`？

这两个字段保存作者长期基础质量信号，由 AI 分析文章后刷新。推荐中的作者质量分会使用它们，用户主页评分也会展示相关结果。

### Q4：`article.status`、`reviewDecision`、`riskLevel` 分别表示什么？

`status` 是文章当前展示状态，如 `PUBLISHED`、`LOW_PRIORITY`、`REVIEW_REQUIRED`、`REJECTED`。`reviewDecision` 是 AI 决策，如 `ALLOW`、`LOW_PRIORITY`、`REVIEW`、`REJECT`。`riskLevel` 是风险等级，如 `LOW`、`MEDIUM`、`HIGH`、`BLOCK`。


### Q6：为什么文章和标签用关联表？

文章和标签是多对多关系，一篇文章可以有多个标签，一个标签也可以属于多篇文章。关联表还能保存权重、置信度等附加信息。


### Q8：`comment.parentId` 和 `replyToUserId` 的作用？

`parentId` 表示评论层级，用于回复某条评论；`replyToUserId` 表示被回复的人，用于通知中心生成“回复了你”的提醒。

### Q11：推荐相关表各自作用是什么？

`reco_event` 记录曝光、点击、点赞、评论、收藏、隐藏、举报等行为；`reco_user_profile` 保存用户画像；`reco_user_seen` 记录已看文章；`reco_article_daily_stat` 按天统计文章表现；`reco_request_log` 记录推荐请求和结果。

### Q12：为什么 `tagVector` 和 `authorAffinity` 用 JSON？

画像是稀疏向量，不同用户的标签和作者数量不固定。用 JSON 保存更灵活，适合当前原型；如果后续做大规模检索，可以拆成向量明细表或引入专门存储。

### Q13：`auth_refresh_token` 为什么只保存 `tokenHash`？

避免数据库泄露时 refresh token 明文可直接使用。系统只用哈希比对令牌，同时支持过期、撤销和轮换。

### Q14：数据库符合第几范式？

核心业务表基本接近第三范式，实体和关系拆分较清楚。推荐画像中的 JSON 是有意的反范式设计，用灵活性换取实现简单。

### Q17：有没有索引？

有。比如文章有 `authorId`、`status + posttime` 索引，审计有 `requestId`、`createdAt` 等索引，推荐事件有 `userId + createdAt`、`articleId + createdAt` 等索引。没有索引会导致列表、推荐、审计查询在数据量增大后变慢。

## 4. 用户认证与权限控制


### Q2：注册时如何处理密码？

注册接口校验用户名、邮箱和密码，密码用 bcrypt hash 后入库，不保存明文。公共注册接口固定创建普通用户，不能传入 `role=admin`。

### Q3：access token 和 refresh token 分别负责什么？

access token 生命周期短，用于访问受保护接口。refresh token 生命周期长，用于刷新会话，并支持撤销和轮换。

### Q4：CSRF token 的作用是什么？

刷新会话时系统会校验 CSRF token，降低跨站请求利用 Cookie 自动携带 refresh token 的风险。它主要保护 Cookie 会话刷新链路。

### Q5：用户退出时凭证如何失效？

退出时服务端把 refresh token 标记为撤销，并清除认证 Cookie。access token 本身较短期，过期后不能再刷新。


### Q10：权限控制在网关层还是服务层？

网关负责统一入口和转发，业务服务负责真正的身份和权限判断。这样即使有人绕过前端或伪造请求，服务层仍能拦截。

### Q11：为什么需要二次权限判断？

因为网关只知道路由，业务服务才知道资源归属。比如删除文章必须查文章作者，读取聊天记录必须查线程参与者。

## 5. 内容发布与审核

### Q1：用户发布文章后经历什么流程？

文章先清洗和校验内容，再以 `PENDING_REVIEW` 写入数据库，然后博客服务调用 AI 服务分析。AI 结果写回文章状态，并通过通知中心反馈给作者。

### Q4：低优先级公开和正常公开有什么区别？

两者都能公开展示，但 `LOW_PRIORITY` 会在推荐排序中受到风险惩罚，展示优先级更低。

### Q8：AI 服务失败时怎么办？

AI 服务会返回保守 fallback，风险较高，决策为 `REVIEW`，文章进入复核。原则是宁可暂不公开，也不让未审核内容直接进入信息流。

### Q9：系统是否支持人工复核？

当前已经有 `REVIEW_REQUIRED` 状态和管理员查看 AI 结果的基础，但完整人工复核工作流还可以继续完善。答辩中可说“支持复核状态和管理查看，人工处理闭环是后续优化方向”。

### Q10：审核结果是否影响用户评分？

会。低优先级、复核、拒绝和举报会降低用户综合评分，也会影响用户表中的专业度和友好度。

## 6. AI 内容分析

### Q1：AI 分析哪些维度？

四个维度：友善度、理性度、合法性、专业性。每个分数范围是 0 到 100。

### Q3：风险等级如何生成？

主要依据合法性分：80 以上为低风险，60 到 79 为中风险，40 到 59 为高风险，40 以下为阻断风险。决策也按合法性分映射为通过、降权、复核或拒绝。

### Q4：审核建议由谁生成？

外部模型或 mock provider 会返回原因和建议，系统再规范化保存。最终文章状态由系统规则根据评分和决策映射，避免完全依赖模型自由判断。


### Q6：AI 返回结果如何保证结构化？

真实 Provider 在 prompt 中要求只返回 JSON，并使用 `response_format: json_object`。服务端还会解析、规范化分数和标签；解析失败则进入保守 fallback。


### Q10：AI 分析结果是否可信？

AI 结果不能视为绝对正确，所以系统保留复核状态、风险原因、管理员查看和通知反馈。高风险内容不会直接公开，误判可以通过人工复核机制改进。

### Q12：AI 分析是同步还是异步？

当前发文流程会同步触发 AI 分析并写回状态，但文章先落库为 `PENDING_REVIEW`，保证安全边界。后续可改为消息队列异步处理，提高并发能力。


## 7. 推荐系统与用户画像

### Q1：推荐系统采用什么思路？

采用“规则过滤 + 用户画像 + 特征加权排序”。先过滤不可展示内容，再按 AI 标签、用户兴趣、作者质量、内容质量、新鲜度、风险和已看记录综合打分。


### Q4：推荐总分由哪些部分组成？

公式口径为：标签匹配 * 4 + 作者亲和 * 2 + 作者质量 * 1.2 + 内容质量 + 新鲜度 - 风险惩罚 - 已看惩罚。

### Q5：标签匹配分是什么？

它计算用户画像 `tagVector` 和文章 AI 标签的匹配程度。用户经常点击、阅读或收藏某类标签内容，对应标签权重会提高。

### Q6：作者亲和度是什么？

表示用户过去对某个作者内容的兴趣。点击、停留、评论、收藏、关注作者等行为会提高亲和度，隐藏和举报会降低。

### Q7：作者质量分来自哪里？

来自作者 `professionalism` 和 `friendliness` 两个基础字段。它们由作者历史文章的 AI 分析结果和审核扣分更新。

### Q8：内容质量分如何计算？

内容质量结合 AI 四项评分、文章近 14 天互动统计和负反馈。高质量互动会加分，隐藏和举报会降权。

### Q11：用户画像多久更新？

推荐服务读取画像时，如果画像不存在或超过 6 小时，会刷新。推荐事件中强行为也会触发画像更新。


### Q13：推荐事件有哪些？

包括曝光、点击、停留、完整阅读、点赞、评论、收藏、关注作者、隐藏和举报。它们权重不同，收藏、评论等强行为权重高，隐藏和举报是负权重。

### Q14：新用户怎么推荐？

新用户没有画像时，系统仍可按内容质量、作者质量、互动统计和新鲜度排序。用户产生行为后，画像逐步形成。

### Q15：新文章没有互动数据怎么办？

新文章仍有 AI 评分、作者质量和新鲜度。后续随着曝光、点击、评论等事件增加，互动统计会逐步影响排序。

### Q16：推荐会不会形成信息茧房？

有这种风险。系统通过新鲜度、已看惩罚、风险惩罚和非单一标签排序缓解，但多样性探索仍是后续优化点。

### Q17：推荐效果如何评价？

推荐专项测试构造了 3 类画像用户、36 个作者、291 篇文章和 1021 条推荐事件。结果显示不同画像用户看到的主题不同，已看惩罚和非公开过滤也生效。

## 8. 用户综合行为评分

### Q1：用户综合评分的目的是什么？

它用于衡量用户历史内容质量、合规情况和互动反馈，为用户主页展示、作者质量信号和平台治理提供依据。

### Q2：为什么公开展示用户评分？

公开评分可以增强平台信任和内容质量激励。但答辩时要补充：生产环境应提供解释、申诉和隐私保护，避免标签化用户。

### Q3：评分由哪些部分组成？

由内容质量分、合规分和互动反馈分组成。综合分权重是内容质量 55%、合规 25%、互动反馈 20%。

### Q4：为什么内容质量占 55%？

平台核心是内容社区，内容质量应是主要依据。合规和互动也重要，但不能让热度完全压过质量。

### Q5：合规分如何扣分？

从 100 分起扣，低优先级每篇扣 4 分，复核每篇扣 12 分，拒绝每篇扣 28 分，举报每次扣 8 分。

### Q6：互动反馈分如何计算？

从 50 分起算，点赞、评论、收藏、关注作者和完整阅读会加分，隐藏和举报会明显扣分。

### Q7：A/B/C/D 如何划分？

综合分 85 及以上为 A，70 到 84 为 B，50 到 69 为 C，低于 50 为 D。

### Q8：评分会不会被恶意刷高或刷低？

有风险。当前通过多信号综合降低单一行为影响，后续应加入反作弊、异常检测和可信用户权重。

### Q9：文章少的用户评分可靠吗？

可靠性较弱。系统会返回“暂无可评价内容”等信号，答辩时可说明低样本用户评分应谨慎解释。

### Q10：用户评分和推荐作者质量有什么关系？

推荐中的作者质量主要使用 `professionalism` 和 `friendliness`，它们来自 AI 分析后的作者基础评分。综合评分则更全面，额外考虑审核结果和互动反馈。

### Q11：评分机制最大不足是什么？

权重主要来自规则设计和测试验证，不是大规模真实用户数据训练得出。后续应结合真实运营数据和人工标注持续校准。

## 9. 社交互动与通知

### Q6：通知如何区分已读未读？

`notification.readAt` 为空表示未读，有时间表示已读。系统支持单条已读和全部已读。

### Q7：评论通知和回复通知如何区分？

评论文章作者时生成 `COMMENT`，回复某个评论用户时生成 `REPLY`。通知里会带 `articleId` 和 `commentId` 方便跳转。

### Q8：互动和推荐如何关联？

点赞、评论、收藏、关注、隐藏、举报等行为会写入 `reco_event`。推荐画像和文章日统计会读取这些事件，影响后续排序。

### Q9：通知写入失败是否影响主流程？

当前实现里部分通知是主流程后的同步 `await`，理论上失败可能影响响应。更稳妥的生产做法是把通知改为异步队列或 try-catch 降级，这可以作为后续优化点。

## 10. 聊天模块

### Q1：聊天功能如何实现？

聊天模块由 `chat_service` 实现，REST 接口负责线程和历史消息，WebSocket 负责实时收发。消息最终写入 `chat_message` 表。


### Q3：为什么使用 WebSocket？

聊天需要服务端主动推送消息，HTTP 轮询实时性差、开销高。WebSocket 更适合双向实时通信。

### Q4：WebSocket 如何经过网关？

网关只为 `/api/chat` 路由开启 WebSocket 升级代理，并转发到 `chat_service` 的 `/chat/ws`。这也是修复过的重点问题。


### Q7：聊天消息是否做内容审核？

目前主要做身份、线程权限和内容长度校验，没有接入 AI 内容审核。答辩时应把它作为当前不足，后续可复用 AI 审核服务处理私信风险。

### Q8：聊天消息是否写入审计日志？

REST 聊天接口会记录线程和消息相关审计，WebSocket 连接也会记录连接审计。当前 WebSocket 每条消息主要写入 `chat_message`，逐条审计还可以补充。


### Q11：聊天模块为什么单独拆成服务？

聊天有 WebSocket 长连接、连接管理和实时推送逻辑，与普通 HTTP 内容接口差异明显，单独拆分便于扩展和隔离。

## 11. 安全设计、审计与运维

### Q1：系统安全性主要体现在哪些方面？

包括认证令牌、refresh token 哈希、CSRF token、角色权限、资源归属校验、输入校验、内容清洗、限流、AI 审核、审计日志和 requestId 追踪。

### Q2：API 网关如何做安全控制？

网关生成或透传 requestId，统一 CORS，使用 `express-rate-limit` 限流，并只代理已配置路由。管理类网关接口还会校验管理员角色。

### Q3：如何防止 XSS？

文章和评论会经过内容清洗，移除 script、iframe、style 等危险标签，并限制链接和图片属性。生产环境还应补充 CSP 和更严格的富文本白名单策略。

### Q4：如何防止 CSRF？

refresh token 使用 HttpOnly Cookie 保存，刷新会话时要求 CSRF token 匹配。Cookie 设置了 SameSite，减少跨站自动携带风险。

### Q5：如何防止 SQL 注入？

主要使用 Prisma 查询和参数化 SQL。少量 `$queryRawUnsafe` 用于通知表动态查询，参数是分离传入的，但生产中仍建议进一步收敛为更安全的查询封装。

### Q6：如何防止未授权和越权访问？

未登录接口用 `requireAuth` 拦截，管理员接口用 `requireRole` 拦截，资源操作再查作者、通知接收人、聊天线程参与者等归属关系。

### Q7：审计日志记录哪些内容？

记录 requestId、用户、角色、IP、方法、路径、动作、结果、状态码、详情和时间。登录、发文、删除、AI 分析、评论、关注、聊天和异常请求都会留下记录。

### Q8：requestId 有什么用？

它把网关请求、业务处理、AI 调用和审计日志串起来。出现异常时可以用同一个 requestId 查找整条链路。


### Q11：为什么审计模块没有独立成服务？

当前审计写入逻辑轻量，分散在各服务中更容易落地。缺点是耦合较高，后续可以抽成独立审计服务或日志管道。

### Q12：运维控制台显示什么？

显示网关健康、上游服务健康、路由列表、路由指标、审计日志和管理员摘要。管理员可根据失败率、热点路由和 requestId 定位问题。

### Q13：系统有没有限流和输入校验？

有。网关使用限流中间件；各服务对字符串、邮箱、密码、分页、ID、emoji、数组长度等做输入校验。

### Q14：和 OWASP Top 10 的对应关系？

认证和角色控制对应身份鉴别与访问控制；内容清洗对应 XSS；Prisma 和参数化查询对应注入防护；审计日志对应安全日志与监控；CSRF token 和 Cookie 策略对应会话安全。

### Q15：还有哪些安全薄弱点？

聊天内容未接入 AI 审核，审计日志不是防篡改存储，通知仍有同步耦合，真实生产还需要 HTTPS、CSP、密钥管理、漏洞扫描、备份和更细的权限策略。

## 12. 系统测试与结果解释

### Q1：采用了什么测试方法？

采用自动化黑盒接口测试、前端页面冒烟测试、WebSocket 测试、压力测试和推荐专项数据验证。黑盒测试从网关入口模拟真实访问。

### Q2：为什么选择黑盒测试？

因为答辩验收更关注系统外部行为是否可用，如注册、登录、发文、评论、关注、通知、聊天和推荐是否能闭环。算法和权限细节再通过灰盒或代码说明补充。

### Q7：压力测试选择哪些接口？

选择网关健康、文章列表、推荐流和当前用户接口。推荐流单独压测，因为它涉及候选文章、画像、AI 标签、已看记录、统计表和曝光写入。

### Q8：推荐流 P95 约 5.03s 是否说明性能差？

说明推荐流还有优化空间，但功能和稳定性已经通过复验。延迟主要来自候选加载、画像刷新、多表统计和同步曝光写入，后续可用缓存、异步写入和 TopK 优化降低。

### Q9：推荐专项测试数据是怎么来的？

是脚本构造的系统测试数据，不是长期真实运营数据。数据包括 3 类画像用户、36 个作者、291 篇文章和 1021 条推荐事件，用于验证画像对推荐排序的影响。

### Q10：测试结果如何支撑论文结论？

功能测试证明主业务闭环可运行，安全测试证明未登录和越权能被拦截，推荐专项证明画像和 AI 标签能影响排序，压力测试暴露并修复了并发写入问题。

### Q11：有没有单元测试、安全渗透测试和真实用户测试？

当前重点是黑盒、压力和专项验证，单元测试、系统性渗透测试、真实用户长期测试仍不足。答辩时应承认这是后续完善方向。

### Q12：现场演示建议演示什么？

建议演示登录、发文、AI 审核结果、通知反馈、文章详情评论、关注、推荐流画像差异、聊天实时消息和运维审计页面。顺序要围绕“发布-审核-展示-互动-追踪”闭环。

## 13. 论文表述与危险追问速答

### Q1：论文题目里的“设计与实现”分别体现在哪里？

“设计”体现在架构、模块划分、数据库、权限、审核和推荐规则；“实现”体现在各服务代码、接口、数据库表、Docker Compose、前端页面和测试报告。

### Q2：“高安全性”会不会过于绝对？

可以解释为相对普通毕业设计原型更强调安全设计，不是宣称达到生产级最高安全。论文中应表述为“具备较完善安全控制能力的社交平台原型”更稳妥。


### Q7：为什么测试用 Mock Provider？

Mock 保证测试稳定、低成本、可重复，不受外部模型网络和额度影响。真实模型用于语义质量提升，Mock 用于验证系统流程和结构。


### Q10：公开用户评分是否有公平性问题？

有潜在问题，尤其是低样本用户、被恶意举报用户。系统目前提供分数解释，后续应加入申诉、反作弊和可见性控制。

### Q11：系统相比现有平台有什么实际改进？

它把内容审核、风险降权、用户评分、推荐画像和审计追踪整合到一个小型社交平台中。重点改进是可解释、可追踪的内容治理闭环。

### Q13：论文数据是真实运行还是测试构造？

主要来自测试构造和自动化验证，不是长期真实运营数据。答辩时要明确这是原型系统验证数据，用于证明功能闭环和规则效果。

### Q14：系统最大不足是什么？

最大不足是仍处于毕业设计原型阶段：共享数据库、推荐性能有优化空间、AI 判断需要人工复核、聊天内容审核不足、缺少真实长期用户数据。
