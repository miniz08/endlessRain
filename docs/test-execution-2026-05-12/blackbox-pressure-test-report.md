## 4. 失败项与缺陷

### 4.1 高风险：注册接口允许客户端指定管理员角色

用例：`SEC-001`  
接口：`POST /api/auth/register`  
预期：普通注册接口不应允许客户端传入 `role=admin`，应返回 400 或 403。  
实际：接口返回 201，并创建了角色为 `admin` 的用户。

影响：

- 任意访问者可能通过注册接口创建管理员账号。
- 管理员账号可进一步访问审计日志、管理员摘要、AI 分析等敏感接口。
- 该问题属于权限边界缺陷，优先级高。

建议：

- 公共注册接口拒绝客户端传入 `role` 字段，并在服务层固定新用户角色为 `user`。
- 角色修改只保留在管理员接口中，并记录审计日志。
- 对已有测试账号或演示账号，使用数据库初始化脚本或受保护的后台接口创建。

### 4.2 中风险：WebSocket 实时广播未在网关路径下送达

用例：`BB-907`  
入口：`ws://127.0.0.1:3001/api/chat/ws`  
预期：用户 A 通过 WebSocket 发送消息后，用户 B 在线连接应收到 `message_created` 事件。  
实际：认证连接可建立，但用户 B 在 7 秒内只收到 `ready` 消息，没有收到实时消息广播。

补充观察：

- REST 聊天能力通过，包括线程创建、发送消息和消息历史查询。
- 未认证 WebSocket 连接被拒绝，通过。
- 已认证 WebSocket 连接可建立，通过。
- 问题集中在“经网关代理后的实时广播送达”环节。
- API 网关日志出现 `MaxListenersExceededWarning`，提示 WebSocket 代理监听器可能存在重复注册或监听器数量过多。

建议：

- 复查 API 网关 `handleProxyUpgrade` 与 `http-proxy-middleware` 的 WebSocket 代理逻辑。
- 只为真正需要 WebSocket 的 chat 路由启用 `ws: true`，避免所有代理路由都注册 upgrade 监听。
- 增加一条双用户 WebSocket 集成测试，分别验证直连聊天服务和经网关代理两种路径。

## 5. 压力测试结果

压力测试共执行 4 组场景，总请求数 600 次。

| 场景 | 请求数 | 并发 | 成功 | 失败 | 吞吐量 | 平均延迟 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 网关健康检查 | 180 | 20 | 180 | 0 | 1496.32 req/s | 12.86ms | 22.57ms | 23.88ms |
| 文章列表 | 160 | 16 | 160 | 0 | 19.88 req/s | 726.54ms | 1416.82ms | 1708.15ms |
| 推荐流 | 160 | 16 | 158 | 2 | 2.21 req/s | 7121.23ms | 8362.98ms | 9454.93ms |
| 当前用户接口 | 100 | 10 | 100 | 0 | 92.46 req/s | 104.16ms | 225.03ms | 345.22ms |

压力测试结论：

- 网关健康检查吞吐量高，延迟很低，说明网关基础响应能力正常。
- 当前用户接口在 10 并发下表现稳定，100 次请求全部成功。
- 文章列表在 16 并发下全部成功，但平均延迟约 726ms，P95 超过 1.4s，有一定优化空间。
- 推荐流是本次压力测试中最慢的接口，平均延迟约 7.1s，P95 约 8.36s，并出现 2 次 500。

推荐流压力失败日志显示：

```text
Invalid prisma.reco_user_seen.upsert() invocation
Unique constraint failed on the constraint: PRIMARY
```

该错误发生在 `blog_service/src/services/recoEventService.ts` 的 `markSeen` 逻辑中。推测原因是并发请求同时对同一用户、同一文章写入 `reco_user_seen`，导致复合主键冲突。虽然使用了 upsert，但在高并发下仍出现冲突，建议改为更稳妥的原子更新或捕获唯一约束冲突后重试。

## 8. 结论

从黑盒测试结果看，系统大部分核心功能已经具备可演示和可验收能力。用户认证、文章发布、AI 审核、评论互动、关注关系、通知、推荐、审计、前端页面和大部分聊天 REST 流程均能完成。

公共注册接口允许创建管理员角色属于高风险权限缺陷，已在后续修复中改为拒绝客户端传入角色字段，并在服务层固定新注册用户为普通用户。修复后定向复验显示，带 `role=admin` 的注册请求返回 400，错误码为 `ROLE_NOT_ALLOWED`。

从压力测试结果看，网关和用户接口表现较稳定，文章列表可用但延迟偏高，推荐流在并发下暴露出写入冲突和性能瓶颈。写入冲突已通过原子写入方式修复；推荐流在 160 次请求、16 并发的定向复验中全部返回 200，但 P95 仍约 5.03s，后续仍需要继续优化推荐候选加载和画像计算耗时。

## 9. 缺陷性质与修复复验

本次失败项可以分为一次高风险安全缺陷和两项有记录价值的结构性工程问题。公共注册接口允许客户端指定 `role=admin` 是确定性结构缺陷，不属于偶发现象；该问题不适合作为系统能力亮点写入论文正文，但必须在报告中记录其发现、修复和复验过程。修复方式为：公共注册接口一旦收到 `role` 字段即返回 400，同时注册服务层固定写入 `role=user`，避免以后其他调用路径再次带入外部角色。

WebSocket 实时消息未送达属于网关代理层的结构性问题。原实现为所有代理路由开启 WebSocket 代理，升级连接的监听范围过大，测试日志中也出现过 `MaxListenersExceededWarning`。修复后只为 chat 路由开启 `supportsWebSocket`，并且网关只把 `/api/chat` 的升级请求转给聊天服务。定向复验中，两个已登录用户通过 `ws://127.0.0.1:3001/api/chat/ws` 建立连接后，接收方可以收到 `message_created` 事件。

推荐流 500 错误属于并发触发的结构性问题，不是普通的网络偶发错误。第一次压力测试暴露的是 `reco_user_seen` 复合主键冲突；继续复验后又发现同类问题也会出现在 `reco_user_profile` 首次并发创建上。最终将推荐热路径中的 `reco_user_seen`、`reco_user_profile` 和 `reco_article_daily_stat` 写入改为 MySQL 原子 `INSERT ... ON DUPLICATE KEY UPDATE`。复验批次 `mp2ekb2ja267` 共执行 7 个定向检查项，全部通过；其中推荐流 160 次请求、16 并发，返回状态全部为 200。
