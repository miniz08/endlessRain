# 系统黑盒测试方案

文档日期：2026-05-07

## 1. 结论

当前系统可以进行黑盒测试，而且黑盒测试非常适合作为系统验收、演示验收和回归验证的主线。

本项目由 Nuxt 前端、API 网关、用户服务、博客内容服务、聊天服务、AI 分析服务和资源服务组成。对测试人员来说，系统已经有比较清晰的外部边界：前端页面、统一 `/api` 网关、WebSocket 聊天入口、健康检查和运维监控接口。因此可以在不理解内部代码实现、不直接访问数据库的前提下，对主要业务闭环进行验证。

不过，系统不建议只依赖黑盒测试。推荐排序、AI 审核、权限角色、通知生成和数据一致性等能力，黑盒测试可以发现结果异常，但很难定位内部原因。因此建议采用以下策略：

- 黑盒测试用于验证系统外部行为、业务流程和验收标准。
- 灰盒或白盒测试用于补充推荐算法、AI 分析规则、权限中间件、数据模型和边界逻辑。
- 本文档只描述黑盒测试方案，不要求当前阶段落地自动化测试脚本。

## 2. 测试目标

黑盒测试需要验证系统对用户和外部调用方是否表现正确，重点目标如下：

- 用户可以完成注册、登录、会话保持、退出登录。
- 用户可以浏览、发布、查看、删除文章。
- 用户可以评论、删除评论、对文章和评论进行 reaction。
- 用户可以关注、取消关注其他用户，并看到关注关系变化。
- 推荐流、关注流、标签页和文章详情页能正常返回内容。
- 通知可以正确产生、展示、统计未读数和标记已读。
- 私聊线程、消息发送、历史消息和 WebSocket 通信可用。
- 网关可以正确代理各业务服务，并提供健康、路由、指标和审计类接口。
- 未登录、无权限、非法参数、资源不存在、服务异常等场景能够返回可理解的错误。
- 前端关键页面无白屏、无明显布局遮挡、无主流程阻断。

## 3. 测试对象

### 3.1 前端页面

主要从用户视角验证以下页面：

| 页面 | 说明 |
| --- | --- |
| `/` | 推荐流、关注流、文章列表、发文入口 |
| `/login` | 登录 |
| `/register` | 注册 |
| `/article/:id` | 文章详情、评论、reaction |
| `/u/:id` | 用户主页、关注信息、私聊入口 |
| `/topic` | 标签分类文章页 |
| `/chat` | 私聊线程和消息收发 |
| `/notifications` | 通知中心 |
| `/ops` | 运维状态、网关健康、监控汇总 |

### 3.2 API 网关入口

系统统一通过 `/api` 暴露后端能力，黑盒测试建议优先从网关入口调用，而不是直接调用内部服务端口。

| 网关路径 | 目标能力 |
| --- | --- |
| `/api/auth` | 注册、登录、会话、退出 |
| `/api/users` | 用户资料、搜索、评分、角色相关能力 |
| `/api/articles` | 文章列表、创建、详情、删除、文章 reaction |
| `/api/comments` | 评论和评论 reaction |
| `/api/following` | 关注列表 |
| `/api/followers` | 粉丝列表 |
| `/api/feeds` | 推荐流、关注流 |
| `/api/reco` | 推荐事件、用户画像 |
| `/api/notifications` | 通知列表、未读数、已读状态 |
| `/api/analysis` | AI 标签、文本分析、文章分析 |
| `/api/chat` | 聊天线程和消息历史 |
| `/api/gateway` | 网关健康、路由、指标、审计和管理摘要 |

### 3.3 WebSocket 入口

聊天服务包含 WebSocket 通信能力。黑盒测试需要验证：

- 未认证连接是否被拒绝。
- 已认证用户是否可以建立连接。
- 双用户在线时，消息是否可以实时送达。
- 断线重连后，历史消息是否仍可通过 REST 接口读取。

## 4. 测试范围

### 4.1 纳入范围

- 用户认证和会话。
- 用户公开资料、搜索和权限接口。
- 内容发布、文章列表、文章详情和删除。
- 评论、删除评论、reaction。
- 关注、取消关注、关注摘要。
- 推荐流、关注流、推荐事件。
- 通知产生、查询、未读数、已读操作。
- 聊天线程、消息发送、消息历史、WebSocket 实时收发。
- AI 分析接口的鉴权和返回结构。
- 网关代理、健康检查、路由检查、指标检查。
- 前端关键页面可用性。
- 异常输入、无权限、未登录、资源不存在、限流等场景。

### 4.2 不纳入纯黑盒范围

以下内容不建议只通过黑盒测试判断：

- Prisma schema 和数据库迁移细节。
- 推荐算法内部权重和排序公式。
- AI prompt 内部质量和模型调用细节。
- 审计日志内部写入逻辑。
- 服务内部函数分支覆盖率。
- 数据库索引、事务隔离和锁等待细节。

这些内容可以在后续通过单元测试、集成测试、数据库检查或灰盒测试补充。

## 5. 测试环境建议

建议准备独立测试环境，避免污染开发数据和演示数据。

| 配置项 | 建议 |
| --- | --- |
| 部署方式 | 使用 `docker-compose.dev.yml` 或独立测试 compose |
| 数据库 | 使用独立测试数据库 |
| AI | 使用 `AI_PROVIDER=mock`，保证结果稳定 |
| 网关 | 统一通过 `/api` 访问后端能力 |
| 前端 | 使用开发端口或测试环境域名访问 |
| 数据重置 | 每轮测试前清理测试用户、文章、评论、聊天和通知 |

建议准备以下测试账号：

| 账号 | 用途 |
| --- | --- |
| 普通用户 A | 注册、登录、发文、关注、聊天发起方 |
| 普通用户 B | 被关注、被评论、聊天接收方 |
| 管理员用户 | 运维页、管理接口、AI 审核类能力 |
| 未登录游客 | 游客访问、未授权拦截验证 |

## 7. 异常和安全测试

黑盒测试需要特别覆盖以下异常与安全场景：

- 未登录访问受保护接口。
- 普通用户访问管理员接口。
- 普通用户访问审核或内部 AI 接口。
- 篡改用户 ID 删除他人文章、评论或读取他人聊天线程。
- 非法 JSON 请求体。
- 空字符串、纯空白、超长文本。
- HTML、脚本标签、特殊字符输入。
- 不存在的用户 ID、文章 ID、评论 ID、通知 ID、线程 ID。
- 重复提交关注、取消关注、reaction、已读等操作。
- 高频请求触发限流。
- cookie、token 缺失、过期、伪造。
- CORS 相关请求是否符合预期。
- WebSocket 未认证连接、重复连接、异常断开。
- 上游服务不可用时，网关是否返回明确错误。
- AI provider 异常时，内容发布和运维页面是否能降级。

| 普通用户 | 至少 2 个 | 关注、评论、聊天、通知 |
| 管理员用户 | 至少 1 个 | 运维、管理、审核 |
| 文章 | 至少 5 篇 | 列表、详情、推荐、标签 |
| 评论 | 每篇至少 1 条 | 评论列表和通知 |
| reaction | 每篇至少 1 个 | reaction 计数和推荐事件 |
| 关注关系 | 至少 1 组 | 关注流和粉丝列表 |
| 聊天线程 | 至少 1 个 | 消息历史和 WebSocket |
| 通知 | 至少 3 条 | 未读数、单条已读、全部已读 |

数据准备可以通过前端手工操作完成，也可以在后续阶段通过接口脚本或测试夹具生成。

## 9. 验收标准

建议使用以下标准判断黑盒测试是否通过：

- P0 主流程全部通过：注册、登录、发布文章、查看文章、评论、关注、通知、聊天。
- 所有受保护接口在未登录时都不能访问。
- 越权操作不能成功。
- 网关未知路由返回统一错误结构，并包含 `requestId`。
- 前端关键页面无白屏、无明显交互阻断。
- WebSocket 聊天至少完成一轮双用户实时收发。
- `AI_PROVIDER=mock` 时，AI 分析返回结构稳定。
- 服务重启后，用户、文章、评论、聊天记录等核心数据仍可读取。
- 常规接口响应时间处于可接受范围。
- 异常场景不会导致前端无限加载、服务崩溃或返回无结构错误。

## 10. 优先级建议

### P0 必测

- 系统健康和网关代理。
- 注册、登录、会话、退出。
- 文章列表、发布、详情。
- 评论和 reaction。
- 关注和关注流。
- 通知列表和未读数。
- 聊天线程、消息发送、WebSocket 收发。
- 未登录和越权拦截。

### P1 建议测

- 推荐事件和用户画像。
- 标签页和标签列表。
- AI 分析接口。
- 运维页面。
- 限流和错误结构。
- 断线重连。

### P2 可延后

- 大量数据下的分页体验。
- 长时间在线 WebSocket 稳定性。
- 多用户并发 reaction 和评论。
- AI 真实 provider 的质量对比。
- 跨浏览器兼容性细节。

## 11. 风险和补充建议

纯黑盒测试存在以下局限：

- 推荐排序是否真正符合预期，需要结合内部评分、画像和事件数据判断。
- AI 分析质量无法只靠接口返回成功来证明，需要人工样本集或评测规则。
- 通知和审计日志是否完全一致，需要灰盒检查数据库或日志。
- 数据库迁移、索引和事务问题，不一定能在小规模黑盒测试中暴露。
- 权限边界需要结合代码审查或接口清单持续维护。

因此建议后续形成三层测试体系：

| 层级 | 作用 |
| --- | --- |
| 黑盒测试 | 验证系统外部行为和业务闭环 |
| 集成测试 | 验证服务之间、服务和数据库之间的契约 |
| 单元测试 | 验证关键规则、校验器、权限判断和推荐策略 |

## 12. 后续可落地方向

虽然当前阶段不要求落地，但如果后续需要自动化，可以按以下顺序推进：

1. 使用 Postman、Apifox 或 REST Client 整理 API 黑盒集合。
2. 使用 Playwright 覆盖登录、发文、评论、关注、聊天等前端主流程。
3. 使用独立测试数据库和固定测试数据，保证每轮测试可重复。
4. 对 WebSocket 聊天补充专门的双用户连接测试。
5. 将 P0 用例接入 CI，作为合并和部署前的验收门槛。
