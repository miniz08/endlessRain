## 第 1 章 绪论

### 1.1 研究背景

随着互联网应用不断发展，社交平台已经成为人们获取信息、表达想法和建立关系的重要渠道。用户可以通过发动态、评论、关注、私信等方式参与交流，平台中的内容更新快、互动多，用户自己产生的内容也越来越多。根据《艾媒咨询 | 2025年中国网络安全产业运行状况与用户行为调查报告》，2025 年中国用户日常获取和传递信息的网络渠道中，社交平台占比最高，达到 61.56%。这说明社交平台已经是互联网信息传播中非常重要的一类应用。

与此同时，生成式人工智能的发展也改变了网络内容的生产方式。自 ChatGPT 推出后，大语言模型逐渐进入大众使用场景，AI 生成文字、图片和多媒体内容的能力不断增强。它一方面降低了内容创作门槛，提高了内容产出速度；另一方面也带来了低质量自动生成内容、虚假信息、垃圾信息等问题。对于社交平台来说，既要保证用户能够正常表达，又要尽量减少有风险的内容，这是平台设计时需要认真考虑的问题。

社交平台还保存了大量用户身份信息、关系数据、发布内容、互动记录和聊天数据，因此安全风险也比较高。比如用户数据泄露、越权访问、恶意请求、批量注册和内容攻击等问题，都可能影响平台稳定运行，也会影响用户对平台的信任。相关网络安全报告显示，网站系统每天都会面对大量自动化攻击和风险扫描，所以安全设计已经成为平台类系统必须具备的基础能力。

基于以上背景，本文设计并实现一个高安全性微服务社交平台。该平台在提供基础社交功能的同时，引入 AI 内容分析、内容评分、用户综合评分、推荐展示、通知反馈和审计日志等设计，希望在保证基本使用体验的基础上，提高平台的内容质量和安全管理能力。

### 1.2 研究目的与意义

本课题的主要目标是设计并实现一个基于微服务思路的社交平台。平台以用户发布内容和社交互动为核心，支持用户注册登录、文章发布、评论回复、Emoji 反馈、关注关系、消息通知、私信聊天、AI 内容评分、用户综合评分、推荐展示和系统审计等功能。通过这些功能，平台可以形成从身份确认、内容发布、AI 审核、内容展示、用户互动、通知反馈到审计查看的完整流程。

从理论意义上看，本课题把社交平台的内容治理问题和 AI 分析能力结合起来。传统内容审核更多关注内容是否违规，而本文中的平台不仅判断内容是否存在明显风险，还从友好程度、理性程度、合法程度和专业程度等角度评价内容质量，并结合用户历史内容和互动反馈形成用户综合评分。这种设计可以为 AI 技术在社交平台内容管理中的应用提供一个较完整的实现案例。

从实践意义上看，本平台采用前后端分离和微服务设计，把用户、内容、AI、聊天、推荐和网关等功能拆开实现，后期维护和扩展会更方便。在安全方面，平台加入了身份认证、角色权限、请求追踪、内容审核状态、通知反馈和审计日志等处理，可以减少未授权访问、内容风险和问题难以追查等情况。在工程实现方面，平台使用 Docker Compose 支持多服务启动，便于开发、演示和后续扩展。

### 1.3 系统整体框架介绍

平台采用前后端分离的微服务结构。前端使用 Nuxt 3、Vue 3 和 TypeScript 实现，主要负责页面展示、用户操作、状态维护和接口调用。后端主要使用 Node.js、Express 和 TypeScript 实现，并通过 API 网关统一提供 `/api` 访问入口。

后端由用户服务、博客内容服务、AI 分析服务、聊天服务和 API 网关组成。用户服务负责注册、登录、刷新令牌、用户资料和权限判断；博客内容服务负责文章、评论、Emoji、关注、通知、推荐流和用户画像；AI 分析服务负责内容评分、风险等级和 AI 标签生成；聊天服务负责单对单私信和 WebSocket 实时通信；API 网关负责请求转发、限流、服务健康检查、运行指标和审计查询。

数据存储使用 MySQL 和 Prisma。为了方便开发和答辩演示，当前多个后端服务共用同一个 MySQL 数据库，但在表结构和代码职责上仍按不同服务进行划分。平台提供 Docker Compose 配置，可以在开发或部署环境中同时启动前端、网关和各个后端服务。

## 第 2 章 系统分析

### 2.1 可行性分析

#### 2.1.1 技术可行性分析

本平台使用的主要技术包括 Nuxt 3、Vue 3、TypeScript、Node.js、Express、Prisma、MySQL、WebSocket 和 Docker。这些技术在当前 Web 应用开发中比较成熟，也有较多资料和实践案例。Nuxt 和 Vue 适合实现交互式前端页面；Node.js 和 Express 适合快速开发接口服务；Prisma 可以让数据库访问更加规范；MySQL 能满足关系型数据存储需要；WebSocket 可以支持私信聊天中的实时消息；Docker Compose 能简化多服务运行环境的搭建。

从服务划分上看，本课题也具备实现条件。平台把用户认证、内容管理、AI 分析、聊天通信和网关转发等功能分成几个独立服务，各部分职责比较清楚，可以分别开发、构建和扩展。服务之间主要通过 HTTP 接口通信，前端只需要访问统一的 API 网关，不需要关心后端具体服务地址。AI 服务通过 provider 设计支持 mock 模式和 OpenAI-compatible 模式，既可以保证测试结果稳定，也为后续接入真实模型留下空间。

在 AI 文本分析方面，当前软件采用免费大模型轮询的方式实现内容评分和标签生成。由于文章审核任务主要是对文本进行分类、打分和结构化结果生成，输入输出规模相对可控，不需要自行训练大模型或部署高成本 GPU 推理服务。系统可以通过 OpenAI-compatible 接口接入多个免费或低成本的大模型服务，并按轮询方式选择可用模型完成分析，从而分散单一免费模型的额度限制和访问压力。模型返回结果后，AI 服务再对四项评分、风险等级、处理决策和标签进行规范化处理，并写入数据库，为后续文章状态更新、推荐展示和用户评分计算提供依据。

免费大模型服务可能存在额度限制、响应变慢或临时不可用等情况，因此该方案在工程上需要配合超时、重试和降级机制。当前 AI 服务已经将模型调用封装在独立 provider 中，外部模型异常时可以返回保守复核结果，使文章进入人工复核或稍后重试流程，避免未分析内容直接公开。模型接口密钥和服务地址通过环境变量配置，内部文章分析接口通过服务 token 调用，不直接暴露给普通用户。由此可见，免费大模型轮询既能满足开发、测试和小规模运行阶段的 AI 文本分析需求，也保留了后续切换付费模型、私有化模型或混合模型池的扩展空间。

因此，从技术选择、服务拆分、数据库访问和部署方式来看，本课题在技术上是可行的。

#### 2.1.2 经济可行性分析

平台使用的主要框架和工具大多为开源技术，不需要额外支付软件授权费用。开发阶段可以在本地电脑运行，也可以部署到普通云服务器上。AI 服务在开发和测试阶段可以使用 mock provider，避免产生真实模型调用费用；如果后续投入实际使用，也可以根据成本和效果选择不同的大模型服务或开源模型。

由于平台采用多个服务组合的方式，初始部署时可以把多个服务放在同一台服务器上，以降低成本。当访问量增大后，再根据实际压力对部分服务单独扩展。因此，从开发、测试和小规模部署角度看，本课题具有较好的经济可行性。

#### 2.1.3 操作可行性分析

从普通用户角度看，平台提供注册登录、浏览内容、发布动态、评论、Emoji 反馈、关注、通知中心和私信聊天等功能，符合常见社交平台的使用习惯，学习成本较低。用户发布内容后，可以通过通知中心看到审核结果和互动提醒，操作反馈比较明确。

从管理员或维护人员角度看，平台提供网关健康检查、路由信息、运行指标、审计日志和管理员摘要，可以了解平台运行情况。当某个服务出现异常时，可以结合健康接口、日志和审计记录定位问题。因此，平台在日常使用和运维管理方面具有操作可行性。

### 2.2 需求分析

#### 2.2.1 功能需求分析

本系统主要面向普通用户、审核管理人员和系统维护人员三类对象。由于平台属于社交内容系统，用户进入系统后并不是只完成单次查询，而是会持续进行发布、浏览、互动、聊天和接收反馈等操作。因此，功能需求需要围绕“用户怎样使用平台”和“平台怎样处理内容”两个方面展开。

普通用户端主要包括以下功能。

（1）注册登录功能。用户首次使用系统时，需要通过用户名、邮箱和密码完成注册；已有账号的用户可以通过用户名或邮箱登录。登录成功后，系统保存会话状态，用户即可进入首页浏览内容、发布文章、评论和聊天。用户退出后，会话失效，需要重新登录才能继续使用受保护功能。

（2）内容发布与浏览功能。用户可以在首页或发布入口填写文章内容和标签并提交。文章提交后不会马上进入公共页面，而是先进入审核流程。用户可以在首页、推荐流、关注流、用户主页和文章详情页查看已经公开的内容，也可以查看自己发布内容的处理结果。

（3）社交互动功能。用户可以关注其他用户，查看关注列表和粉丝列表；可以在文章下发表评论或回复评论；也可以对文章和评论添加 Emoji 反馈。对于一对一沟通场景，平台提供私信聊天功能，用户可以进入聊天线程发送和接收消息。

（4）通知反馈功能。用户发布内容后，系统会把 AI 审核结果反馈到通知中心；当其他用户评论、回复、添加 Emoji 或关注自己时，也会产生通知。用户可以查看通知列表、未读数量，并将通知标记为已读。

（5）个人主页和综合评分功能。用户主页展示用户基础资料、发布内容、关注关系和综合行为评分。综合评分不是单独填写的静态信息，而是根据文章质量、审核状态和互动反馈计算得到，用于反映用户在平台中的内容表现。

审核管理人员端主要包括以下功能。

（1）AI 分析与内容处理查看。审核员或管理员可以查看文章 AI 分析结果，包括友好度、理性度、合法性、专业度、风险等级、处理原因和处理建议。对于进入复核状态的内容，系统需要保留足够的信息，方便后续人工判断。

（2）审计日志与运行状态查看。管理员可以查看网关健康状态、路由指标、审计日志和失败请求摘要。系统出现异常时，可以通过请求 ID、用户 ID、接口路径和状态码定位问题。

（3）权限管理功能。普通用户不能访问审计和管理类接口，审核员和管理员根据角色获得不同范围的访问能力。角色控制需要贯穿网关、业务服务和具体接口。

系统维护层主要包括以下功能。

（1）多服务转发与健康检查。API 网关负责把前端请求转发到用户服务、博客服务、AI 服务和聊天服务，并提供健康检查接口。

（2）推荐画像与行为记录。用户浏览、点击、停留、点赞、评论、收藏、关注、隐藏和举报等行为会写入推荐事件表。系统根据这些事件计算用户画像，并在推荐流中改变文章排序。

（3）数据一致性维护。用户、文章、评论、关注、通知、AI 分析、推荐事件和聊天数据之间存在较多关联，系统需要通过唯一约束、外键关系和事务处理保证数据能够正确增删改查。

#### 2.2.2 安全需求分析

本系统保存用户账号、发布内容、互动记录和聊天数据，安全需求主要体现在登录身份、接口权限、内容展示和运行追踪四个方面。

第一，登录身份需要可靠。用户登录后由系统签发 access token 和 refresh token，其中 refresh token 不以明文保存，而是保存哈希值，并支持刷新和撤销。这样用户退出登录或刷新会话时，旧令牌不会继续有效。

第二，不同角色的接口入口需要分开。普通用户可以发布文章、评论、关注和聊天，但不能访问审计日志、网关指标和 AI 管理类接口。审核员和管理员可以进入管理相关接口，但删除文章、删除评论、查看聊天线程等操作仍需要检查数据归属，避免只凭登录状态就操作他人数据。

第三，内容公开前需要经过处理。文章发布后先保存为 `PENDING_REVIEW`，随后由 AI 服务生成分析结果。只有 `PUBLISHED` 和 `LOW_PRIORITY` 状态可以进入公共列表、关注流和推荐流；`REVIEW_REQUIRED`、`REJECTED` 等状态不能被普通访问者看到。这样可以避免未审核或高风险内容直接出现在平台首页。

第四，系统运行过程需要可追踪。API 网关会为请求生成或传递 `requestId`，业务服务在响应和审计日志中保留该标识。登录、发布、删除、AI 分析、评论、关注、聊天和异常请求等关键行为会写入 `audit_log`。当某个接口出现失败时，可以根据请求 ID 回看相关链路。

### 2.3 系统流程分析

本系统的整体流程可以按照普通用户、内容处理、推荐展示和管理员查看四条线来说明。

#### 2.3.1 普通用户使用流程

普通用户进入平台后，首先选择注册或登录。登录成功后，用户可以进入首页浏览公开文章，也可以进入推荐流查看系统根据画像生成的内容。若用户需要发布内容，则在发布框中填写正文和标签并提交。提交完成后，文章先进入待审核状态，用户可以等待通知中心返回处理结果。

用户在浏览内容时，可以进行评论、回复、添加 Emoji、关注作者和私信聊天等操作。这些操作会改变前端页面中的互动状态，也会在后端生成通知、推荐事件和审计记录。用户再次进入推荐流时，系统会根据新的行为记录调整推荐排序。

#### 2.3.2 内容审核与展示流程

文章发布后，博客服务先保存文章基础信息，再调用 AI 分析服务。AI 服务会对文章生成四项评分、风险等级、处理决策、原因、建议和标签。博客服务根据处理决策修改文章状态：允许发布的文章进入 `PUBLISHED`，需要降低推荐优先级的文章进入 `LOW_PRIORITY`，风险较高的文章进入复核或拒绝状态。

公开展示时，首页列表、关注流和推荐流只读取公开状态内容。文章详情页则根据访问者身份判断是否能查看非公开内容：作者本人可以查看自己的处理结果，审核员和管理员可以查看复核相关内容，普通访问者不能查看。

#### 2.3.3 推荐反馈流程

推荐流不是单纯按照发布时间展示。系统先读取公开候选文章，再结合用户画像、AI 标签、作者评分、文章质量、发布时间、风险惩罚和已看记录进行排序。推荐结果返回后，系统会把本次结果写入推荐请求日志，并把每篇返回文章记录为曝光事件。

当用户点击、停留、阅读完成、点赞、评论、收藏、关注、隐藏或举报文章时，这些行为会继续写入推荐事件表，并更新文章日统计和用户画像。由此形成“推荐展示、用户行为、画像更新、再次推荐”的闭环。

#### 2.3.4 管理员查看流程

管理员或审核员登录后，可以进入运维页面查看服务健康、网关路由指标、审计日志和失败请求摘要。若某个操作出现异常，可以结合请求 ID、接口路径、用户 ID 和状态码进行排查。该流程主要用于保障系统运行过程中的可观察性。

## 第 3 章 总体设计

### 3.1 系统整体功能模块设计

本平台的功能结构围绕“用户发布内容、系统处理内容、用户继续互动、管理员查看运行情况”展开。结合前端页面和后端服务划分，系统可以分为八个主要模块。

（1）用户认证与权限管理模块。该模块是系统入口，主要完成注册、登录、退出、刷新会话、当前用户识别和角色判断。用户登录成功后才能进行发布、评论、关注和聊天等操作。审核员和管理员访问审计、AI 管理和运维接口时，还需要进一步进行角色校验。

（2）社交内容发布与管理模块。该模块负责文章发布、文章列表、文章详情、用户主页文章、标签和删除操作。文章发布后先进入审核状态，再根据 AI 处理结果决定是否公开展示。

（3）用户社交关系与互动模块。该模块包括关注、取消关注、粉丝列表、关注列表、评论、回复、文章 Emoji、评论 Emoji 和私信聊天。用户之间的互动既会改变页面展示，也会产生通知和推荐事件。

（4）消息通知与处理反馈模块。该模块把文章审核结果、评论、回复、Emoji 和关注等反馈统一放入通知中心。用户可以查看未读数量，也可以将单条或全部通知标记为已读。

（5）AI 内容评分模块。该模块负责调用 AI 分析服务，生成文章的友好度、理性度、合法性、专业度评分，同时生成风险等级、处理决策、原因、建议和 AI 标签。

（6）用户综合行为评分模块。该模块根据用户发布内容的 AI 分数、审核状态和互动反馈计算综合评分，并在用户主页中展示评分等级和风险信号。

（7）推荐与展示模块。该模块负责首页列表、关注流和推荐流。推荐流会读取用户画像、AI 标签、作者质量、内容质量、已看记录和风险分级，计算排序结果。

（8）安全日志记录与审计模块。该模块记录关键请求和运行指标，管理员可以根据审计日志、网关健康和路由指标判断系统是否正常运行。

### 3.2 数据库设计

#### 3.2.1 数据库概念结构设计

数据库概念结构主要围绕用户、文章、评论、关注、通知、AI 分析、推荐事件、聊天和审计日志等实体展开。用户是系统中最基础的实体，文章、评论、关注、聊天和通知都直接或间接与用户相关。

从实体关系看，用户与文章是一对多关系，一个用户可以发布多篇文章；文章与 AI 分析是一对一关系，一篇文章对应一条当前分析结果；文章与评论是一对多关系，一篇文章可以拥有多条评论；用户与用户之间通过关注表形成多对多关系；文章与标签之间通过关联表形成多对多关系；用户与文章之间还会通过推荐事件、已看记录和 Emoji 反馈形成多种行为关系。

推荐相关数据与普通社交数据也存在联系。用户浏览、点击、评论和点赞文章时，会产生推荐事件；推荐事件再计算出用户画像；用户画像又会影响后续推荐流中的文章排序。这样数据库中的内容、行为和推荐结果能够形成连续的数据链路。

#### 3.2.2 数据库逻辑结构设计

根据系统功能，数据库表可以按用途分为六类。

第一类是用户与认证表，主要包括 `user` 和 `auth_refresh_token`。`user` 表保存用户名、邮箱、密码哈希、角色、头像、个人简介以及专业度和友好度等评分字段；`auth_refresh_token` 表保存刷新令牌哈希、过期时间和撤销时间，用于维持登录会话。

第二类是内容与互动表，主要包括 `article`、`comment`、`article_reaction` 和 `comment_reaction`。`article` 表保存文章正文、作者、发布时间、标签和审核状态；`comment` 表保存文章评论、回复关系和评论状态；两个 reaction 表保存用户对文章或评论添加的 Emoji。

第三类是社交关系和通知表，包括 `follow` 和 `notification`。`follow` 表使用关注者和被关注者的组合表示用户关系；`notification` 表保存审核结果、评论提醒、回复提醒、Emoji 提醒和关注提醒。

第四类是 AI 分析表，包括 `article_ai_analysis`、`article_ai_tag` 和 `article_ai_tag_on_article`。分析表保存四项评分、风险等级、处理原因和建议；标签表保存 AI 生成的标签名称；关联表保存文章与 AI 标签之间的权重和置信度。

第五类是推荐画像表，包括 `reco_event`、`reco_request_log`、`reco_user_profile`、`reco_user_seen` 和 `reco_article_daily_stat`。这些表分别记录用户行为事件、每次推荐返回的结果、用户画像、用户已看记录和文章每日统计。

第六类是聊天与审计表，包括 `chat_thread`、`chat_message` 和 `audit_log`。聊天线程表用于确定两个用户之间的会话，聊天消息表保存消息正文和阅读状态；审计日志表保存关键请求信息，便于管理员排查问题。

在逻辑约束上，系统为邮箱、用户名、关注关系、reaction、聊天线程等字段设置唯一约束，避免重复数据。对于文章列表、推荐事件、通知和审计日志等高频查询数据，系统按用户、文章、状态、请求 ID 和创建时间建立索引，提高查询效率。

#### 3.2.3 数据库物理结构设计

物理结构上，本系统使用 MySQL 存储数据，并通过 Prisma schema 描述表结构。文章正文使用 `LongText` 类型保存，原因是社交平台中的文本长度不固定；通知内容、审核原因和审核建议使用 `VarChar` 控制长度，避免字段过大。推荐画像和推荐结果列表属于半结构化数据，使用 JSON 字段保存较为方便。

在实际运行中，文章列表、推荐流、通知中心和审计查询访问频率较高。因此，文章表围绕作者、状态和发布时间建立索引；推荐事件表围绕用户、文章、事件类型和请求 ID 建立索引；通知表围绕用户和已读状态建立索引；审计日志表围绕请求 ID、用户 ID、结果和创建时间建立索引。通过这些索引，系统可以更快地查询公开信息流、未读通知、用户画像来源和失败请求记录。

### 3.3 系统架构设计

系统采用前后端分离和微服务组合的结构。前端由 Nuxt 3 实现，负责页面展示、状态管理和接口调用。后端通过 API 网关统一对外提供 `/api` 入口，网关再根据路径转发到不同业务服务。

用户服务主要处理注册、登录、会话刷新、用户资料和用户评分查询；博客服务处理文章、评论、关注、通知、推荐流和用户画像；AI 服务处理文章内容分析、评分和标签生成；聊天服务处理会话线程、聊天消息和 WebSocket 实时通信；API 网关负责请求转发、限流、健康检查、路由指标和审计查询。

从一次完整业务看，用户发布文章时，前端请求先进入网关，再转发到博客服务；博客服务写入文章后调用 AI 服务获取分析结果；分析结果再回写文章状态和 AI 表；用户随后在通知中心看到处理反馈。用户浏览和互动时，博客服务会继续写入推荐事件和通知数据。管理员查看系统状态时，则主要通过网关提供的健康检查、指标和审计接口完成。

当前各服务共用同一个 MySQL 数据库，便于开发、测试和答辩演示；但代码层面已经按照服务职责拆分，后续可以进一步演进为独立数据库或独立部署的服务。

## 第 4 章 系统详细设计及实现

### 4.1 用户认证与权限管理模块

#### 4.1.1 用户注册、登录与会话管理

用户认证部分由 `user_service` 实现。注册时，平台会校验用户名、邮箱和密码格式，并检查用户名和邮箱是否已经被使用。密码经过哈希处理后再写入数据库，避免明文保存。登录时，平台根据用户名或邮箱查找用户，并校验密码哈希。校验通过后，平台签发 access token、refresh token 和 CSRF token。

access token 用于短时间内识别用户身份，refresh token 用于延长登录会话。平台只保存 refresh token 的哈希值，并记录过期时间、用户代理和 IP 地址。当用户刷新会话时，旧 refresh token 会被撤销并替换为新的 token。用户退出登录时，平台撤销 refresh token，使当前会话失效。

从代码实现看，注册入口位于 `user_service/src/controllers/authController.ts`。控制器先调用 `assertUsername`、`assertEmail` 和 `assertPassword` 做输入校验，再进入 `authService.registerUser`。服务层使用 `bcrypt.hash` 保存密码哈希，并通过 `prisma.user.findFirst` 检查用户名或邮箱是否重复。登录成功后，`issueTokens` 负责生成 JWT access token、refresh token 和 CSRF token，其中 refresh token 会经过 SHA-256 哈希后写入 `auth_refresh_token` 表。刷新会话时，`refreshTokens` 使用数据库事务撤销旧 token 并创建新 token，避免旧刷新令牌长期有效。

> 图 4-1 插入位置：用户认证流程图。Mermaid 源文件：[auth-flow.mmd](../diagrams/modules/auth-flow.mmd)

#### 4.1.2 角色权限与接口访问管理

平台通过登录校验逻辑识别当前用户，再根据用户角色控制敏感接口访问。普通用户可以发布内容、评论、关注、聊天和查看自己的通知；审核员或管理员可以访问 AI 分析接口、审计日志和管理员摘要等功能。对于删除文章、删除评论、查看聊天线程等操作，平台还会检查资源归属，防止用户操作不属于自己的数据。

权限边界主要由 `requireAuth` 和 `requireRole` 中间件实现。`requireAuth` 从 Bearer token 或 Cookie 中取出 access token，校验后把用户 id、用户名和角色挂载到 `req.auth`。需要管理员能力的接口再叠加 `requireRole`。公开注册路径不接收客户端提交的角色字段，并在 `authService.registerUser` 中固定写入 `role=user`；角色变更只保留在受保护的管理员接口中，从而把“注册身份”和“管理授权”分开处理。

### 4.2 社交内容发布与管理模块

#### 4.2.1 内容发布、查询与删除实现

内容发布部分由 `blog_service` 实现。用户发布文章时，前端调用 `/api/articles`，服务端对内容进行基本校验和清洗，然后写入 `article` 表。文章查询接口支持首页列表、用户主页列表、标签查询和文章详情查询。删除文章时，操作者必须是文章作者或管理员，同时需要清理评论、reaction、标签关联和 AI 分析关联。

文章列表和详情会返回作者信息、AI 分析结果、AI 标签、普通标签、评论数量和 reaction 汇总。前端通过文章卡片组件展示内容、标签、评分和互动入口。

核心发布逻辑集中在 `blog_service/src/services/articleService.ts` 的 `createArticle`。服务先用 `sanitizeContent` 清洗正文，再以 `PENDING_REVIEW` 状态写入 `article` 表，并通过 `syncManualTags` 同步普通标签。随后 `requestAiAnalysis` 调用 AI 服务，`applyReviewResult` 根据 AI 返回的 decision 更新文章状态、风险等级、审核原因和建议。删除文章时，`deleteArticle` 会在事务中清理评论、reaction、普通标签关系、AI 标签关系和 AI 分析记录，避免文章删除后留下孤立数据。

#### 4.2.2 发布前审核与文章状态处理

为了避免未审核内容直接进入信息流，平台为文章设置了审核状态。新文章创建后状态为 `PENDING_REVIEW`，随后调用 AI 服务进行分析。AI 决策为 `ALLOW` 时，文章进入 `PUBLISHED` 状态；决策为 `LOW_PRIORITY` 时，文章进入低优先级公开状态；决策为 `REVIEW` 时，文章进入复核状态；决策为 `REJECT` 时，文章进入拒绝状态。

公开列表、关注流和推荐流只展示 `PUBLISHED` 和 `LOW_PRIORITY` 内容。复核、拒绝和待审核内容不会进入公开信息流。作者本人可以查看自己的非公开内容详情，并通过通知中心获得处理结果。

文章可见性由 `isPublicArticleStatus` 和 `canViewArticle` 两层判断完成。列表和推荐候选只加载公开状态内容；详情接口则允许作者本人、审核员和管理员查看非公开内容。这个实现使“公开展示”和“作者查看处理结果”可以同时存在，不会因为文章暂未公开就让作者无法确认审核反馈。

### 4.3 用户社交关系与互动功能

#### 4.3.1 关注关系与用户关系维护

关注功能通过 `follow` 表保存。用户关注他人时，平台会创建或恢复关注关系，并禁止用户关注自己。用户可以查看关注列表、粉丝列表和关注摘要。关注摘要包括关注数、粉丝数以及当前访问者是否已关注该用户。关注行为还会生成通知，并记录为推荐事件，用于更新用户画像。

代码上，`followService.followUser` 先拦截自我关注，再确认目标用户存在，最后通过 `prisma.follow.upsert` 创建或恢复关系。取消关注不是删除记录，而是把状态改为 `INACTIVE`。关注列表、粉丝列表和关注摘要都会额外计算 `followedByMe`，前端可以直接根据该字段展示关注按钮状态。

#### 4.3.2 评论、回复与 Emoji 互动实现

平台支持文章评论、评论回复、文章 Emoji 和评论 Emoji。创建评论时，平台先检查文章是否为公开状态，再写入评论表。回复评论时，平台会记录父评论和被回复用户。Emoji 反馈使用联合唯一约束，保证同一用户对同一对象的同一 Emoji 不会重复写入；用户再次点击同一 Emoji 时，会取消该反馈。

当他人评论用户文章、回复用户评论或对文章/评论添加 Emoji 时，平台会在通知中心生成提醒。评论、Emoji 和关注等互动行为也会写入推荐事件，参与用户画像和内容质量统计。

评论创建由 `commentService.createComment` 完成，服务会先确认文章处于公开状态，再写入评论或回复关系。Reaction 使用“切换”逻辑：`reactionService.toggleArticleReaction` 和 `toggleCommentReaction` 会先查找同一用户、同一对象、同一 emoji 是否已存在，存在则删除，不存在则创建。私信聊天由 `chatService.getOrCreateThread` 和 `createMessage` 实现，两个用户 id 会先排序后写入复合唯一线程，WebSocket 收到 `send_message` 后也复用同一套 `createMessage` 写库逻辑，再向双方在线连接广播 `message_created`。

### 4.4 消息通知与处理结果反馈功能

通知功能由 `blog_service` 实现，通知数据保存在 `notification` 表中。平台支持通知列表、未读数量、单条已读和全部已读操作。前端通知中心按时间倒序展示通知，导航栏显示未读数量。

通知来源主要有两类：一类是内容处理结果，例如审核通过、低优先级展示、进入复核、审核拒绝或审核失败；另一类是社交互动反馈，例如评论、回复、文章 Emoji、评论 Emoji 和关注。平台会避免用户自己对自己内容操作时产生通知，从而减少没有意义的提醒。

通知写入统一经过 `notificationService.createNotification`。该函数会先调用 `ensureNotificationStore` 确保通知表存在，再插入通知记录；如果 `actorId` 与接收人相同，则直接返回，不生成自触发通知。审核反馈由 `notifyArticleReviewResult` 根据文章状态映射通知类型，评论、reaction 和关注分别由 `notifyCommentCreated`、`notifyArticleReaction`、`notifyCommentReaction` 和 `notifyFollowed` 生成。已读操作使用 `COALESCE(readAt, CURRENT_TIMESTAMP(3))`，重复标记不会改变第一次阅读时间。

### 4.5 基于 AI 分析的内容评分功能

#### 4.5.1 AI 分析服务接入与调用流程

AI 内容评分由 `ai_service` 实现。文章创建后，`blog_service` 使用内部服务 token 调用 AI 服务，避免普通用户直接访问内部分析接口。AI 服务读取文章内容后，通过 provider 调用 mock 模型或外部大模型接口。开发和测试环境可以使用 mock provider，保证分析结果稳定；生产环境可以切换到 OpenAI-compatible provider。

AI 分析接口受到权限保护，只有审核员、管理员或内部服务请求可以调用。如果模型调用失败，平台会返回较保守的复核结果，使文章进入复核状态，避免未审核内容直接公开。

AI 服务通过 `createProvider` 选择 provider。测试环境使用 `AI_PROVIDER=mock`，可以保证相同文本得到稳定结果；正式环境可切换到 OpenAI-compatible provider。`analysisService.analyzeText` 会把正文和压缩后的标签体系交给 provider，如果 provider 抛出异常，则返回 `fallbackResult`，其中风险等级为 `HIGH`、决策为 `REVIEW`，使文章进入复核流程。

#### 4.5.2 内容评分、标签与风险等级生成

AI 服务从友好度、理性度、合法性和专业度四个角度对文章评分，并生成风险等级、处理决策、原因、建议和标签。评分结果写入 `article_ai_analysis` 表，AI 标签写入 `article_ai_tag` 和关联表。平台根据处理决策更新文章状态，并刷新作者基础评分。

持久化逻辑位于 `persistArticleAnalysis`。它对 `article_ai_analysis` 做 upsert，保证同一篇文章只有一条当前分析记录；AI 标签先按名称去重，再写入 `article_ai_tag` 和 `article_ai_tag_on_article`，同时清理本次未返回的旧标签。随后 `statusFromDecision` 将 `ALLOW`、`LOW_PRIORITY`、`REVIEW`、`REJECT` 映射到文章状态，并调用 `refreshUserRating` 更新作者在 `user` 表中的专业度和友好度。

### 4.6 用户综合行为评分功能

#### 4.6.1 用户评分指标与数据来源

用户综合行为评分由 `user_service` 提供查询接口，数据来源包括文章 AI 评分、文章审核状态和推荐事件反馈。AI 评分反映内容质量，审核状态反映内容是否合规，推荐事件反映用户内容获得的互动情况。

正向反馈包括点赞、评论、收藏、关注作者和阅读完成等行为；负向反馈包括隐藏和举报。平台同时统计用户发布内容数量、低优先级数量、复核数量和拒绝数量，用来解释用户评分。

评分接口的核心代码在 `user_service/src/services/userService.ts` 的 `getUserRating`。该函数并行执行两类聚合查询：一类从文章和 AI 分析表计算四项平均分以及各审核状态数量，另一类从推荐事件表计算正向反馈、完整阅读、负向反馈和举报数。这样评分不是单独依赖用户表中的静态字段，而是结合了内容质量、审核结果和真实互动。

#### 4.6.2 综合评分与用户等级计算

平台把用户评分拆分为内容质量分、合规分和互动反馈分。内容质量分来自 AI 四项评分；合规分根据低优先级、复核、拒绝和举报进行扣分；互动反馈分根据正向互动加分，根据隐藏和举报扣分。最终综合分由三类分数加权生成，并划分为 A、B、C、D 四个等级。

用户主页展示综合等级、综合分、内容质量分、合规分、反馈分和风险信号。风险信号用于说明评分来源，例如低优先级内容数量、复核内容数量、举报次数等。

综合分采用加权计算：内容质量分占 55%，合规分占 25%，互动反馈分占 20%。合规分从 100 分起扣，低优先级、复核、拒绝和举报的扣分逐步加重；互动反馈分从 50 分起算，正向反馈和完整阅读加分，隐藏和举报扣分。最后通过 `levelFromScore` 映射为 A、B、C、D 四档，并由 `buildRatingSignals` 生成可读的风险说明。

### 4.7 基于评分结果的推荐与展示功能

#### 4.7.1 推荐流、关注流与用户画像

推荐与展示功能由 `blog_service` 实现，前端通过 `/api/feeds/recommended` 访问推荐流，通过 `/api/feeds/following` 访问关注流。关注流的逻辑相对直接，系统先查询当前用户关注了哪些用户，再拉取自己和已关注用户发布的公开文章，并按发布时间返回。推荐流则更侧重个性化，会根据用户历史行为和文章质量重新排序。

推荐流的具体过程如下：用户访问推荐页后，服务端先读取当前用户 ID。如果该用户已有画像并且更新时间不超过 6 小时，则直接使用已有画像；如果画像不存在或已经过期，则重新根据推荐事件刷新画像。随后系统从文章表中加载候选内容，候选范围只包含 `PUBLISHED` 和 `LOW_PRIORITY` 两类公开状态。为了保证分页时有足够排序空间，候选数量取 `max(80, limit * 8)`。

候选文章加载完成后，系统会同时读取四类辅助数据：文章 reaction 汇总、评论数量、最近 14 天的文章日统计，以及当前用户对这些文章的已看次数。之后每篇文章都会进入 `scoreArticle` 计算推荐分。推荐分的主要组成如下：

```text
推荐总分 =
标签匹配分 * 4
+ 作者亲和度 * 2
+ 作者质量分 * 1.2
+ 内容质量分
+ 时间新鲜度
- 风险惩罚
- 已看惩罚
```

其中，标签匹配分来自用户画像中的标签权重和文章 AI 标签之间的匹配；作者亲和度来自用户过去对该作者文章的点击、阅读、点赞、评论、收藏或负反馈；作者质量分来自用户表中的专业度和友好度；内容质量分综合 AI 四项评分、文章近期互动质量和负反馈；时间新鲜度使较新的文章略有优势；风险惩罚用于降低合法性分较低或低优先级内容的排序；已看惩罚用于减少同一用户反复看到同一篇文章。

用户画像保存在 `reco_user_profile` 表中，主要包括标签向量和作者亲和度向量。画像不是人工填写，而是由 `reco_event` 中的行为记录计算出来。系统会读取最近 90 天内最多 500 条推荐事件，不同事件有不同权重，例如点击、停留、阅读完成、点赞、评论、收藏和关注作者为正向反馈，隐藏和举报为负向反馈。旧事件会通过时间衰减降低影响，使近期兴趣更能影响推荐结果。

推荐结果返回以后，系统还会写入 `reco_request_log`，保存本次请求的候选数量和返回文章 ID；同时把返回给用户的文章逐条记录为 `IMPRESSION` 事件，并更新 `reco_user_seen`。因此推荐流不是一次性的查询，而是一个“推荐、曝光、行为、画像刷新、再次推荐”的循环。

#### 4.7.2 评分结果对内容展示的影响

评分结果对展示的影响主要分为两层：第一层是能否展示，第二层是展示时排在什么位置。

在能否展示方面，普通列表、关注流和推荐流只允许 `PUBLISHED` 和 `LOW_PRIORITY` 内容进入。`PENDING_REVIEW` 表示文章仍在等待审核，`REVIEW_REQUIRED` 表示需要人工复核，`REJECTED` 表示审核拒绝，这些状态都不会进入普通用户的信息流。推荐流还会检查 AI 合法性分，如果合法性分低于 40，即使异常进入候选，也会被可见性判断挡住。

在排序位置方面，`PUBLISHED` 内容可以正常参与推荐计算；`LOW_PRIORITY` 内容虽然可以公开，但会受到风险惩罚，因此通常不会排在最靠前的位置。这样设计的原因是：低优先级内容并不一定要完全隐藏，但平台也不应主动强化推荐。通过降权处理，可以在公开展示和内容治理之间取得平衡。

用户综合评分也会进入推荐排序。用户表中的专业度和友好度会形成作者质量分，评分较高作者的内容在主题匹配相近时更容易获得靠前位置；如果作者多次发布低优先级、复核或拒绝内容，其专业度和友好度会受到影响，后续内容的展示优先级也会降低。

推荐事件写入由 `recoEventService.recordRecoEvent` 统一处理。该函数会先确认文章仍属于公开状态，再写入事件记录。曝光事件会更新已看次数；点击、停留、阅读完成、点赞、评论、收藏、关注作者、隐藏和举报等强行为会触发用户画像刷新。高并发测试中曾发现已看记录、用户画像和文章日统计在首次并发写入时可能出现主键冲突，因此这些高频写入已经改为 MySQL 原子 `INSERT ... ON DUPLICATE KEY UPDATE`，以保证并发请求下仍能正确累计数据。

### 4.8 安全日志记录与审计模块

#### 4.8.1 请求追踪与关键操作日志记录

平台通过 API 网关为请求生成或传递 `requestId`。各业务服务在处理关键操作时写入 `audit_log`，记录请求 ID、用户、角色、IP、请求方法、路径、操作类型、结果、状态码和详情。审计日志覆盖登录注册、文章发布、AI 分析、评论、reaction、关注、聊天和异常请求等场景。

请求追踪可以帮助平台在出现错误时定位问题来源。对于跨服务请求，例如文章发布后调用 AI 分析，`requestId` 可以帮助管理员关联内容创建、AI 处理和通知反馈等多个环节。

网关中的 `assignRequestId` 会读取或生成 `x-request-id`，并把它写回响应头。各服务的 `writeAuditLog` 使用同一请求 ID 写入 `audit_log`。业务服务在写审计日志失败时只记录错误，不阻断主流程，这样审计系统异常不会影响用户发布、评论或登录等核心功能。

#### 4.8.2 网关监控、审计查询与异常分析

API 网关提供健康检查、路由列表、路由指标、审计日志查询和管理员摘要接口。健康检查会访问各上游服务的 `/health` 接口，并汇总服务状态。路由指标记录请求次数、错误次数、请求方法、最后状态码和延迟。管理员摘要会统计最近一段时间内的成功率、失败率、热点接口和失败请求。

运维页面 `/ops` 展示网关健康、路由指标、审计日志和 AI 分析查询结果。普通用户不能访问审计数据，只有管理员或审核员角色可以查看。

网关状态由 `api_gateway/src/gatewayStatus.ts` 提供。`collectGatewayMetrics` 在响应结束时记录路由请求数、错误数、最后状态码和延迟；`gatewayHealthController` 会访问各上游服务的 `/health` 并汇总为 `ok`、`degraded` 或 `down`。审计查询和管理员摘要会先解析 access token，并只允许 `reviewer` 或 `admin` 角色访问。WebSocket 升级也放在网关层处理，目前只有 chat 路由配置了 `supportsWebSocket`，避免普通 HTTP 代理错误接管升级连接。

## 第 5 章 系统测试

### 5.1 测试环境

系统测试在 Windows 本地环境中完成，通过 Node 进程分别启动前端、API 网关、用户服务、博客服务、AI 服务和聊天服务。测试时没有直接调用服务内部函数，而是尽量模拟普通用户从网关进入系统后的真实访问过程。

各服务端口如下：API 网关运行在 3001 端口，博客服务运行在 3002 端口，用户服务运行在 3003 端口，AI 服务运行在 3004 端口，聊天服务运行在 3005 端口，前端运行在 3000 端口。HTTP 测试入口统一为 `http://127.0.0.1:3001`，WebSocket 测试入口为 `ws://127.0.0.1:3001/api/chat/ws`。这种方式保留了“前端、网关、多个后端服务、数据库”组合运行的链路，更接近系统实际部署后的访问方式。

测试时 AI 服务使用 mock provider，保证同一类文本能够得到稳定的审核结果，避免外部模型波动影响测试结论。网关限流阈值在测试中适当调高，主要观察业务接口和推荐写入本身的表现。测试用户包括普通用户 A、普通用户 B、管理员用户和未登录游客。普通用户 A 用于注册、登录、发布文章、评论、关注和聊天；普通用户 B 用于接收评论、关注和聊天；管理员用户用于查看运维和审计接口；游客用于验证公开访问和未授权拦截。

测试结果和日志保存在 `docs/test-execution-2026-05-12` 和 `docs/recommendation-display-test-2026-05-12` 下，包括黑盒测试结果、压力测试结果、定向复验结果、推荐展示专项结果和各服务日志。这些原始文件可以对应到本章中的测试结论。

### 5.2 测试方案

本次测试主要采用黑盒测试方法。测试脚本从系统外部发起请求，只关注输入和输出是否符合预期，不直接依赖内部函数返回。测试内容包括功能测试、安全测试、异常测试、压力测试和推荐展示专项测试。

功能测试主要验证用户在页面和接口中能否顺利完成核心操作，测试项包括注册、登录、会话刷新、文章发布、文章审核、文章列表、文章详情、评论、Emoji、关注、通知、私信聊天、AI 分析、用户评分和推荐流。

安全测试主要验证接口是否存在越权情况，测试项包括未登录访问受保护接口、普通用户访问管理员接口、删除他人文章、访问非公开文章、无效 token 访问和未知 API 路径访问。

异常测试主要验证系统对错误输入的处理情况，例如重复注册、错误密码、非法参数、资源不存在、重复关注、重复 reaction、AI 服务失败和 WebSocket 未登录连接。

压力测试选取四类接口：网关健康检查、文章列表、推荐流和当前用户接口。每组设置固定请求数和并发数，统计成功数、失败数、吞吐量、平均延迟、P95 和 P99。推荐流单独压测，是因为该接口会同时读取候选文章、AI 标签、用户画像、已看记录、reaction 汇总、评论数和文章日统计，并且还会写入推荐请求和曝光事件，更容易暴露并发问题。

推荐展示专项测试用于验证用户画像和 AI 评分机制是否真正影响推荐结果。该测试批量写入带有明确主题、作者质量、AI 标签、审核状态和历史行为的测试数据，再分别以数据型用户、生活型用户和安全型用户访问推荐流，观察推荐主题是否随画像变化。

### 5.3 测试过程与结果分析

（1）登录功能测试。测试用户输入正确账号和密码后可以进入系统，并访问当前用户接口；输入错误密码时，系统返回认证失败；未登录用户访问发布文章、评论、关注和聊天接口时会被拦截。管理员接口只允许具备相应角色的账号访问。登录功能测试结果如下表所示。

| --- | --- | --- |
| 输入正确账号和密码登录 | 登录成功，可以访问当前用户信息 | 成功 |
| 输入错误密码登录 | 返回认证失败 | 成功 |

（2）文章发布与审核测试。普通用户发布文章后，系统先把文章保存为待审核状态，再调用 AI 服务进行分析。AI mock 返回允许发布时，文章进入公开状态；返回低优先级时，文章可以公开但推荐会降权；返回复核或拒绝时，文章不会出现在公开列表中。测试中，用户能够在通知中心收到文章处理结果，公开文章可以进入首页和推荐流。

| 测试内容 | 预期结果 | 实际结果 |
| --- | --- | --- |
| 用户发布合法文章 | 文章进入审核后公开展示 | 成功 |
| AI 返回低优先级 | 文章可展示但推荐降权 | 成功 |

| 作者查看自己的非公开文章 | 可以查看处理结果 | 成功 |

（3）互动与通知测试。用户 A 评论用户 B 的文章后，用户 B 的通知中心出现评论提醒；用户 A 对用户 B 的文章添加 Emoji 后，用户 B 收到 reaction 提醒；用户 A 关注用户 B 后，用户 B 收到关注通知。评论、Emoji 和关注操作同时会写入推荐事件，为后续画像计算提供数据。

（4）聊天功能测试。测试脚本先通过 REST 接口创建两个用户之间的聊天线程，再通过 WebSocket 连接网关聊天地址。未登录连接会被拒绝；登录用户连接成功后会收到 ready 消息；发送消息后，接收方能够收到 `message_created` 事件。该测试说明聊天服务和网关 WebSocket 转发能够正常配合。

（5）推荐流与用户画像测试。推荐流测试包括基础推荐和专项大规模数据验证。基础测试中，用户访问推荐流后，系统返回公开文章，并写入曝光事件。专项测试批次为 `rdisp_mp2lkdct_82d2ca`，共写入 3 个画像用户、36 个作者用户、291 篇文章、1021 条推荐事件和 1 条已看记录。测试将用户分为数据型、生活型和安全型三类，分别写入不同主题的点击、阅读、点赞、收藏、隐藏和举报行为。

专项测试结果显示，数据型用户的推荐主题集中在数据分析、AI 模型和后端架构；生活型用户的推荐主题集中在旅行记录、生活方式、产品设计和影像评论；安全型用户的推荐主题集中在安全审计、金融观察和后端架构。三类用户推荐结果明显不同，说明用户画像能够影响推荐排序。同时，已看文章相对于同类未看文章排序下降，说明已看惩罚生效；展示流没有返回非公开文章，说明展示控制逻辑有效。

（6）审计与异常测试。管理员访问运维页面时，可以查看服务健康、路由指标、审计日志和失败请求摘要。未知 API 路径会返回统一错误结构，并带有请求 ID。非法参数、资源不存在、无效 token 等异常情况也能返回明确错误。

综合黑盒测试批次为 `mp2d9cgqbf8f34`，共执行 84 个黑盒用例，通过 82 个，通过率为 97.62%。通过内容包括网关健康检查、注册登录、会话刷新、文章发布、评论、reaction、关注、推荐事件、通知、AI 分析、审计查询、前端页面访问和大部分聊天流程。

压力测试共执行 600 次请求。网关健康检查 180 次全部成功；文章列表 160 次全部成功；当前用户接口 100 次全部成功；推荐流 160 次中成功 158 次，失败 2 次。失败日志显示推荐事件写入 `reco_user_seen` 时发生复合主键冲突，说明推荐流并发写入路径存在结构性问题。

针对该问题，后续执行定向复验批次 `mp2ekb2ja267`。修复后，普通注册、聊天线程创建、WebSocket ready、WebSocket 消息送达和推荐流并发复验全部通过。推荐流复验为 160 次请求、16 并发，全部返回 200，P95 约 5.03s。推荐展示专项测试中，推荐流 80 次请求、并发 10，也全部返回 200，但 P95 约 13.7s，说明推荐功能正确，但推荐接口仍是系统中耗时较高的部分。

测试结果表明，平台主要功能流程能够形成闭环，内容发布前审核、通知反馈、用户综合评分、推荐画像、展示控制和审计追踪均具备可演示能力。后续仍可继续优化推荐接口性能，补充人工复核后台和更完整的负反馈入口。

## 第 6 章 总结与展望

本文设计并实现了一个高安全性微服务社交平台。平台采用 Nuxt 3 前端、Node.js 后端服务、API 网关、MySQL 数据库和 Prisma ORM，完成了用户认证、内容发布、评论互动、关注关系、通知中心、私信聊天、AI 内容评分、用户综合评分、推荐展示和审计监控等功能。

在内容治理方面，平台引入 AI 分析服务，对文章进行四项评分、风险等级判断和标签生成。文章发布后先进入待审核状态，再根据 AI 决策进入公开、低优先级、复核或拒绝状态。这种做法避免了未审核内容直接进入公开信息流。平台还把内容评分、审核结果和互动反馈纳入用户综合行为评分，使用户质量管理有更清楚的数据依据。

在安全性方面，平台实现了用户身份认证、角色权限控制、资源归属检查、请求追踪、审计日志和网关监控。管理员可以通过运维页面查看系统健康、路由指标和审计记录，从而提高平台运行过程中的可观察性。

本平台仍有进一步完善空间。后续可以增加人工复核后台，使 `REVIEW_REQUIRED` 内容具备完整处理流程；可以增加举报和隐藏的前端入口，使负向反馈更加完整；可以将当前共享数据库拆分为多个独立数据库，提高各服务的独立性；可以进一步完善推荐算法和用户画像更新策略；也可以增加自动化测试和性能压测，提高平台稳定性。

总体而言，本课题完成了一个兼顾基础社交功能、AI 内容治理、安全管理和推荐展示的微服务社交平台原型，具有一定的工程实践价值和研究意义。
