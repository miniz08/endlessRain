# 论文查重与 AIGC 风格风险辅助审阅

审阅对象：`docs/thesis-draft/main-text-v2.md`

说明：本报告是基于文本风格、重复表达、引用完整性和项目实现细节的人工辅助审阅，不等同于知网、维普、万方或学校系统的正式查重/AIGC 检测结果。

## 1. 总体判断

当前正文没有明显的大段照搬痕迹，技术事实也能对应到项目代码。但从文本风格看，第 1 章、第 2 章、第 3 章和第 6 章仍有一定模板化风险，主要表现为：

- 背景、意义、可行性、总结部分使用了较常见的论文套话。
- 需求分析和总体设计部分的句式过于整齐，容易显得像统一生成的功能清单。
- “平台”“服务”“AI”“评分”“推荐”“审核”等词出现频率较高，虽然符合主题，但会让段落读起来比较机械。
- 测试章节目前偏流程描述，缺少具体测试结果数据或截图编号，因此原创性证据还不够强。

整体风险建议判断：

| 项目 | 风险等级 | 说明 |
| --- | --- | --- |
| 查重相似风险 | 中等 | 通用背景、可行性分析、需求分析容易与同类论文表达接近 |
| AIGC 风格风险 | 中等偏高 | 结构规整、句式稳定、列表化明显，部分段落缺少个人实现细节 |
| 引用风险 | 中等 | 第 1 章引用了报告和网络安全结论，需要在参考文献中完整列出 |
| 项目原创性支撑 | 中等 | 第 4 章较好，但仍可补充更多代码级实现细节、接口、状态流和测试记录 |

## 2. 高频表达观察

对正文做了粗略词频检查，部分词出现次数如下：

| 词语 | 出现次数 |
| --- | ---: |
| 平台 | 95 |
| 服务 | 75 |
| AI | 68 |
| 评分 | 56 |
| 推荐 | 52 |
| 审核 | 40 |
| 通知 | 44 |
| 审计 | 38 |
| 可以 | 55 |

这些词本身不是问题，但如果连续段落都用“平台应支持”“服务负责”“可以实现”“形成流程”这类表达，就会增加模板感。建议后续修改时，用更多具体动作替换抽象表达，例如：

- 将“平台应支持用户发布文章”改为“用户提交文章后，前端通过 `/api/articles` 进入博客服务，服务端先写入待审核状态”。
- 将“服务负责请求追踪”改为“网关在请求进入时生成 `requestId`，并通过 `x-request-id` 传给后续服务”。
- 将“推荐事件用于更新画像”改为“曝光、点击、停留、评论等事件写入 `reco_event`，再参与 `reco_user_profile` 的更新”。

## 3. 重点风险段落

### 3.1 第 1 章：背景与意义

风险位置：

- `1.1 研究背景` 第 9、11、13、15 行
- `1.2 研究目的与意义` 第 19、21、23 行

风险原因：

- “随着互联网应用不断发展”“与此同时”“基于以上背景”“从理论意义上看”“从实践意义上看”等表达属于论文常见框架。
- 第 9 行引用了《艾媒咨询 | 2025年中国网络安全产业运行状况与用户行为调查报告》和 61.56% 数据，必须在参考文献中完整保留来源。
- 第 13 行“相关网络安全报告显示”表述较泛，容易被认为证据不足。

建议：

- 保留必要背景，但减少宏观空话。
- 增加“本课题为什么选择社交平台 + AI 审核 + 微服务”的个人选题理由。
- 对第 13 行补明确来源，或改为“从常见攻击场景看”并结合项目中的限流、审计、请求追踪展开。

### 3.2 第 2 章：可行性与需求分析

风险位置：

- `2.1.1 技术可行性分析` 第 41、43、45 行
- `2.2.1 功能需求分析` 第 65-79 行
- `2.2.2 安全需求分析` 第 83-93 行

风险原因：

- 技术可行性段落与很多 Web 系统论文的写法接近：列技术、说成熟、说可行。
- 功能需求使用“第一、第二、第三……”整齐罗列，虽然清楚，但 AIGC 风格较强。
- “平台应支持……”重复出现，句式单一。

建议：

- 在第 41 行附近加入具体版本或项目选择理由，例如为什么前端选 Nuxt 3、为什么使用 Prisma 统一类型、为什么 AI 服务支持 mock provider。
- 在第 65-79 行把部分“平台应支持”改成用户故事式表达，例如“普通用户登录后，可以完成发文、评论、关注和私信；管理员则主要面向审计和运行状态查看”。
- 安全需求部分可以加入项目实际实现点：`refresh token` 哈希保存、`requestId` 透传、`audit_log` 记录、文章状态从 `PENDING_REVIEW` 到公开/复核/拒绝。

### 3.3 第 3 章：总体设计与数据库设计

风险位置：

- `3.1 系统整体功能模块设计` 第 109、111 行
- `3.2.2 数据库逻辑结构设计` 第 129、131、133 行
- `3.2.3 数据库物理结构设计` 第 137、139 行

风险原因：

- 第 111 行是典型“各模块负责……”句式，信息密度高，但读起来像说明书。
- 第 129 行一次列出大量表名，查重风险不高，但可读性较差，也容易显得机械。
- 数据库设计缺少“为什么这样设计”的解释。

建议：

- 将第 111 行拆成两段：一段讲用户和内容主流程，一段讲 AI、推荐和审计如何接入主流程。
- 第 129 行可以保留表名，但后面补充 2-3 个关键关系设计，例如文章与 AI 分析一对一、关注关系联合唯一、reaction 防重复。
- 增加一句“当前共享数据库是为了降低演示部署复杂度，代码层面仍保留服务边界”，这能体现项目取舍。

### 3.4 第 4 章：详细设计与实现

风险位置：

- `4.1.1 用户注册、登录与会话管理` 第 153、155 行
- `4.2.2 发布前审核与文章状态处理` 第 173、175 行
- `4.5.1 AI 分析服务接入与调用流程` 第 205、207 行
- `4.6.2 综合评分与用户等级计算` 第 225、227 行
- `4.7.1 推荐流、关注流与用户画像` 第 233、235 行
- `4.8.1 请求追踪与关键操作日志记录` 第 251、253 行

风险原因：

- 这些段落比前几章更贴近项目，查重风险较低。
- 但部分表达仍停留在“做了什么”，缺少“怎么做”和“边界如何处理”。

建议加入的真实项目细节：

- 用户认证：说明 cookie 名称或 token 用途，例如 `ls_access_token`、`ls_refresh_token`、`ls_refresh_csrf`。
- 内容审核：说明 `statusFromDecision` 的映射关系，`ALLOW -> PUBLISHED`、`LOW_PRIORITY -> LOW_PRIORITY`、`REJECT -> REJECTED`，其他情况进入 `REVIEW_REQUIRED`。
- AI 接入：说明开发/测试使用 `AI_PROVIDER=mock`，未知 provider 会回退到 mock，真实模型使用 OpenAI-compatible provider。
- 推荐：说明候选内容只取 `PUBLISHED` 和 `LOW_PRIORITY`，曝光、点击、停留、评论、Emoji 等行为会写入推荐事件。
- 审计：说明网关生成 `requestId` 后通过 `x-request-id` 传给后端服务，审计记录按请求 ID 串联跨服务流程。

### 3.5 第 5 章：系统测试

风险位置：

- 第 267-289 行

风险原因：

- 测试章节目前更像测试计划和流程说明，缺少具体结果证据。
- “可以访问”“会返回”“会出现提醒”这类表达较多，但没有测试编号、接口响应、截图引用或结果表格。

建议：

- 增加测试用例表，至少列出：用例编号、测试目标、输入、预期结果、实际结果。
- 在正文中引用 2-3 个关键测试结果，例如注册登录、内容审核状态变化、普通用户访问管理员接口被拒绝、未知 API 返回统一错误结构并包含请求 ID。
- 如果有截图，可以在测试章节标注“图 5-1 登录成功结果”“图 5-2 审核通知结果”“图 5-3 运维页面审计日志结果”。

### 3.6 第 6 章：总结与展望

风险位置：

- 第 293-301 行

风险原因：

- 总结部分整体准确，但表达偏通用，很多毕业论文都会写“完成了……功能”“仍有进一步完善空间”。

建议：

- 加入一两句个人实现反思，例如“本课题在实现过程中发现，AI 审核结果不能只停留在单次文章处理上，因此进一步把审核结果与用户评分、推荐展示联系起来”。
- 展望部分可以从已实现边界出发，比如“当前人工复核后台还没有形成完整操作页面，`REVIEW_REQUIRED` 内容主要停留在状态标记，因此后续需要补上人工处理流程”。

## 4. 优先修改建议

建议按以下顺序处理：

1. 先补引用：第 9 行的报告、第 13 行的网络安全报告必须落实到参考文献。
2. 再改第 1、2、6 章的套话：减少“随着、与此同时、从理论意义、从实践意义、因此”等固定句式。
3. 强化第 4、5 章：加入接口、状态、表名、请求 ID、测试结果这些项目独有证据。
4. 调整重复词：不必刻意删除“平台”“服务”，但要减少连续句子都用同一主语开头。
5. 保留必要专业词：不要为了降低术语频率把关键概念全部口语化，尤其是 token、WebSocket、Prisma、审计日志、推荐事件等词需要准确。

## 5. 可直接加强的表达方向

后续改写时，可以优先把以下几类句子改得更具体：

- “平台支持某功能”改为“用户在某页面/接口提交请求后，后端怎样处理”。
- “系统提高安全性”改为“哪些操作被拦截、哪些记录被写入、出现异常时怎样追踪”。
- “推荐结合用户画像”改为“哪些行为写入推荐事件，哪些文章能进入候选集”。
- “测试结果表明”改为“某个用例的实际结果是什么，是否符合预期”。

如果只做一轮修改，最值得改的是第 1 章背景、第 2 章需求分析、第 5 章测试结果。这三处对查重和 AIGC 风格判断的影响最大。
